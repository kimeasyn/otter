# Otter

**IDE without code · Managing visualized agents like company**

사람 한 명이 AI 직원에게 일을 맡기고, 사무실·대화·문서·보고로 개발을 진행하는 작업공간입니다.
코드 직접 편집은 VS Code 같은 외부 IDE에 맡깁니다.

현재는 새 요구사항으로 **v2 재구현 중**입니다. 배포 가능한 MVP 완성본이 아닙니다.
기준은 [MVP 요구사항 정의서](docs/MVP_REQUIREMENTS_V2.md), 진행 상황은
[구현·검증 기록](docs/IMPLEMENTATION_V2.md)을 참고하세요.

## 실행

Node.js 24 이상, pnpm 10, Git이 필요합니다. 실제 직원 실행에는 실행 환경에 설치하고
로그인한 Codex CLI가 필요합니다. 구독 계정을 범용 API 키로 변환하지 않습니다.

```bash
pnpm install
pnpm build
pnpm start
```

개발용 화면은 `http://127.0.0.1:4318`입니다. 토큰을 붙여 넣지 않고 열 수 있으며,
동일 출처 확인과 HttpOnly 세션 쿠키를 사용합니다. 외부 공개 서버로 노출하지 마세요.
폴더는 실행부가 동작하는 컴퓨터의 폴더이며, 브라우저로 파일을 업로드하지 않습니다.
기존 v1의 4317 포트와 데이터는 별개입니다.

처음 업무를 맡기기 전에 **실행 환경 → Codex 준비 상태 확인**을 사용할 수 있습니다.
로컬/연결된 SSH·WSL마다 CLI 연결, 계정 설정, 네트워크를 허용하지 않은 샌드박스의
OS 기본 명령을 각각 검사합니다. 모델 생성이나 프로젝트 파일 수정은 하지 않습니다.
로그인 정보가 있다는 것이 세션 유효성·잔여 사용량·실제 모델 접근을 보장하지는 않습니다.
실패 항목의 안내를 따라 해당 환경을 확인하세요. 샌드박스를 해제해서 우회하지 않습니다.
진단 결과는 현재 화면에만 표시하며 인증 정보·원시 명령 출력은 보고/대화에 저장하지 않습니다.

설치 앱이 Codex를 찾지 못하면 같은 화면의 **Codex 실행 파일 설정**을 펼치세요.
로컬 설치형 앱에서는 **파일에서 선택…**으로 실행 파일을 고를 수 있습니다. 브라우저 또는
SSH/WSL에서는 해당 실행 환경에 있는 파일의 절대 경로를 입력합니다. Windows는 실제 `.exe`를
선택하며 명령 인수·로그인 키는 입력하지 않습니다. 경로를 비우면 기본 `codex` 탐색으로 돌아갑니다.
신뢰하는 실행 파일인지 확인하고 동의한 뒤 저장하세요. 환경별로 저장되며, 대기 업무를 포함한
다음 직원 실행과 진단에 적용됩니다. 실행·진단 중에는 변경할 수 없고 다른 화면에서 바꾼 설정은
덮어쓰지 않습니다. 저장만으로 지정 파일을 실행하거나 계정을 복사하지 않으며, 저장 후 준비 상태를
별도로 확인합니다. 선택한 경로를 실행하지 못해도 다른 파일로 자동 대체하지 않습니다.

설치형 앱 개발 실행:

```bash
pnpm build
pnpm desktop
```

Electron 화면에 네이티브 폴더 선택과 창 닫기/완전 종료 동작을 연결했습니다.
macOS/Windows 개발용 패키지 생성은 `pnpm desktop:package`입니다. 각 대상 OS에서 실행하며,
Linux에서는 `pnpm desktop:package --dir`로 앱 폴더/포함 파일을 검사합니다.
[패키징 명령·데이터 위치·미검증 범위](docs/DESKTOP_PACKAGING_V2.md)를 먼저 확인하세요.
`pnpm desktop:runtime <app.asar 경로>`로 실제 패키지 실행부의 Electron/SQLite/HTTP/Git 검사를,
`pnpm desktop:smoke`로 개발 런타임의 기본 창/종료 검사를 실행할 수 있습니다.
현재 Linux 검사 환경의 GTK 및 Chromium 샌드박스 조건 때문에 데스크톱 수용 검사는
완료하지 못했습니다. macOS/Windows 설치 패키지 역시 아직 배포하지 않습니다.
보호 설정을 끄는 실행 옵션을 제품 기본값으로 사용하지 않습니다.

완전 종료를 시작하면 새 요청과 대기 업무의 실행을 막습니다. 이미 접수한 병합·푸시는
화면 연결이 끊어져도 결과 기록까지 기다린 뒤 DB를 닫습니다. 승인해 실행한 배포 명령도 종료 기록을 기다립니다. 로컬·WSL 업무는 중단하고,
SSH 서버의 업무는 유지합니다. 처리 중에는 종료 대기 상태를 표시합니다. 프로세스 종료를
확인하지 못하면 DB와 실행부 잠금을 유지하므로 강제로 잠금을 삭제하지 말고 상태를 확인한 뒤
완전 종료를 다시 시도하세요. OS 강제 종료·전원 차단의 안전한 완료까지 보장하는 동작은 아닙니다.

설치형 앱의 최초 화면 로드가 실패하거나 화면 프로세스가 종료되면 **화면 다시 불러오기 / 백그라운드 유지 /
Otter 완전 종료**를 선택할 수 있습니다. 화면 복구는 업무를 다시 요청하거나 실행부를 재시작하지 않습니다.
저장하지 않은 입력은 복구되지 않을 수 있습니다. 백그라운드 유지 후에는 트레이/메뉴의 **사무실 열기**로
다시 시도하세요. 시작 도중 오류나 종료 요청이 발생해도 생성된 실행부의 종료를 확인하며,
종료 실패 안내에서는 상태 유지 또는 명시적 종료 재확인을 선택할 수 있습니다.

## 로컬 기록 사본 저장

설치형 앱의 **Otter → 로컬 기록 백업…** 또는 **설정 → 로컬 기록 백업**에서 범위를 확인하고
새 `.sqlite` 파일의 저장 위치를 선택할 수 있습니다. 모든 로컬 회사·직원·지침·대화·보고·설정과
원격 조회 캐시를 포함합니다. 프로젝트 원본/직원 작업 파일, 원격 실행부의 원본 DB, 인증 파일,
저장하지 않은 입력은 포함하지 않습니다. 선택한 프로젝트만의 백업이나 전체 환경 백업이 아닙니다.

사본은 **암호화되지 않습니다**. 대화·지침에 입력한 비밀 정보는 포함될 수 있으므로 개인이 보호하는
위치에 보관하세요. POSIX 파일 권한은 소유자 읽기/쓰기로 생성하지만 Windows ACL은 별도 검증이 필요합니다.
기존 파일은 덮어쓰지 않습니다. SQLite 검사와 저장된 파일의 해시 검증을 마친 뒤 완료를 표시하며,
앱 완전 종료는 진행 중인 저장/검증을 기다립니다. 실패 후 대상 파일이 남았다면 완료된 사본으로 취급하지 마세요.

**자동 복원·업무 재개는 아직 지원하지 않습니다.** 사본에는 보존용 표식이 있어 실행용 DB로 열면 거절합니다.
현재 `otter.db`에 덮어쓰거나 표식을 지워 재실행하지 마세요. 실행 환경·작업 파일·대기 업무 상태를 확인하는
명시적 복원 절차가 별도로 필요합니다. 브라우저 개발 화면에는 네이티브 저장 기능을 제공하지 않습니다.
파일 복사 라이브러리 대신 [Node SQLite 백업 API](https://nodejs.org/api/sqlite.html#sqlitebackupsourceDb-path-options)의
온라인 사본을 만든 뒤 새 파일에만 저장합니다. 자동/원격/저장소 포함 백업의 범위는 아직 미확정입니다.

## 현재 연결된 흐름

Codex의 명령·파일 변경·추가 접근 권한 요청은 대화/보고 화면에서 확인합니다. 추가 파일 읽기,
쓰기·삭제 경로와 네트워크 범위를 표시하며, 명령/네트워크 승인에는 범위 확인이 필요합니다.
`request_permissions`는 요청한 범위 전체를 현재 턴에만 허용하거나 거절할 수 있습니다.
현재 턴의 후속 명령에도 적용되며 세션 전체 승인·영구 허용 규칙으로 저장하지 않습니다.
해석할 수 없는 권한, 연결을 확인하지 못한 Codex 내부 실행 환경, 다른 대화/오래된 턴의 요청은
승인하지 않습니다. SSH/WSL의 Otter 실행부 선택과 Codex 내부 실행 환경 선택은 별개입니다.
Codex가 `environmentId: local`을 보내면 같은 실행 연결의 `environment/info` 조회 결과가 직원 작업 폴더와
일치해야 합니다. 승인 요청의 현재 폴더도 해당 작업 폴더 내부인지 실제 경로로 확인하고, 승인 직전에 다시
검사합니다. 조회 실패·미지원·다른 환경 ID·외부로 향하는 링크는 자동 허용하지 않습니다.
여기서 local은 Codex가 동작하는 실행부 기준이며 브라우저를 연 PC라는 뜻이 아닙니다.
이 승인은 제공자가 보내온 권한 요청의 처리이며, 모든 임의 명령의 Git·배포·비용 정책을
Otter가 완전히 강제한다는 뜻은 아닙니다. 완료 후 Git 자동 반영 옵션은 아래 별도 설정을 사용합니다.

- 회사 생성 → 기존 Git 저장소 연결 또는 새 저장소 생성 → 직원 생성/배정.
  프로젝트/직원 준비 중에는 입력 변경과 창 닫기를 막습니다. 회사 생성 후 프로젝트 연결이 실패하면
  같은 회사를, 직원 생성 후 배정이 실패하면 같은 직원을 선택한 채 재시도합니다.
  이미 생성된 회사·직원은 창을 닫아도 보존되며, 다시 열 때 목록에서 선택할 수 있습니다.
- 아이디어 회의실 → PM과 질문·답변 → 문서·팀 제안 승인 → 저장 위치 확정 → 개발 요청.
- 도트 사무실 직원 클릭 → 1:1 업무 요청 → 격리된 Git worktree에서 Codex 실행.
- 사무실 말풍선의 업무 제목 클릭 → 해당 업무 대화·질문/승인으로 이동. 확인할 업무 목록에서
  다른 대기 요청도 찾을 수 있습니다. 진행 중 업무가 없으면 최근 실패·중단·완료 결과를 표시하며,
  연결이 끊기면 마지막 확인 상태로 안내하고 작업 애니메이션을 멈춥니다.
- 실제 권한 요청을 화면에서 확인 → 승인/거절 → 보고 확인 → 사용자 검토 완료.
- 선택한 업무의 대화에서 상태·실패 이유·관련 보고를 확인하고 원래 대화로 돌아올 수 있습니다.
  업무 카드·보고에서 대화를 열면 그 업무의 원래 1:1/프로젝트 대화방과 담당 직원을 유지합니다.
  단체방에서도 ‘대화 이어가기’ 상태의 요청은 기존 업무·담당자로 전달합니다. 다른 대화방의
  업무를 필터로 보고 있다면 **원래 업무 대화 열기**로 이동한 뒤 요청합니다.
  보고 화면에서는 업무 범위·보고 종류와 제목/내용/담당 직원 검색으로 기록을 찾습니다.
  과거 보고와 최근 확인한 업무 상태, 직원 보고와 별도 검증 결과는 구분합니다.
  질문·승인은 보고 검색과 별도이며 선택한 업무 범위의 대기 요청을 유지합니다.
- 프로젝트 문서 직접 편집, 직원 설정 스냅샷, 작업 한도와 대기열.
- 저장소 루트 지침 파일 발견·비교·가져오기·명시적 반영, 외부 변경 충돌 및 작성 중인 문서 보호.
- 직원의 공유 지식 제안/사용자 직접 작성 → 공유 승인 → 같은 회사의 다른 프로젝트에서 선택 적용.
- PM 업무 배정과 의존 관계, 직원 → 리뷰어 → PM의 Git 결과 인계 및 대화 재개.
- 신규 직원 채용/문서 변경 제안 승인, 원본 직원 편집·파생·선택 업데이트.
- 프로젝트 대화·직원 간 메시지·업무 스레드와 별도 보고.
  대화 입력은 Enter로 전송하고 Shift+Enter로 줄바꿈합니다. 한글 조합 중 Enter와 키 반복은
  전송하지 않으며, 승인 대기·전송 중 등 기존 전송 불가 조건을 유지합니다.
- 프로젝트 보관/복원. 실제 디렉토리·파일·Git 브랜치·기록은 삭제하지 않습니다.
- 실행 환경 등록 → SSH 연결 → 원격 폴더 탐색·프로젝트 생성·직원 배정·문서/업무 관리.
- 원격 연결 해제 후 저장된 상태 표시, 재연결, 요청 ID를 이용한 중복 생성 방지.
- 프로젝트별 완료 후 원본 반영·푸시·배포 옵션, 고정 대상/명령 승인, 자동 처리 상태와 별도 보고.
- 로컬/원격의 수동 배포 명령 승인, 실행 상태·실패 확인과 별도 보고. 실제 서비스 성공은 별도 확인합니다.

권한 정책별 자동화와 독립 검증, 원격 환경 관리의 나머지 흐름, WSL 실기기 검증,
설치 패키징은 진행 중입니다.
현재 자동 테스트 통과를 이 기능들의 완성 증거로 취급하지 않습니다.

Codex가 요청하는 실행 권한은 자동 승인하지 않습니다. 기본 브랜치 병합·푸시·배포의
완전한 정책 강제는 아직 수용 검증 전이므로, 현재 프리뷰를 중요한 회사 저장소의
무인 자동 실행에 사용하지 마세요. 기본 설정에서는 결과를 작업 브랜치 사이에서 인계하며 원본에 자동 통합하지 않습니다.
최종 업무의 **원본에 반영…**에서 내용을 확인하고 명시적으로 승인하면 원본에 병합할 수 있습니다.

## 원격 실행 프리뷰

사이드바의 **실행 환경**에서 SSH 환경을 등록하고 연결합니다. 이후 프로젝트 시작 화면에서
해당 환경을 선택하면 그 서버의 폴더를 탐색합니다. 로컬 파일 선택창을 원격 폴더 선택에 사용하지 않습니다.

- 해당 서버에 Node.js 24 이상, Git, 업무에 사용할 CLI/로그인이 준비되어 있어야 합니다.
  비대화형 SSH에서 `node`를 찾지 못하면 고급 설정에 Node 실행 파일의 절대 경로를 지정합니다.
- 기존 SSH 설정·키·에이전트를 이용합니다. 먼저 터미널에서 서버의 호스트 키를 확인하고
  비밀번호 입력 없이 접속 가능하게 준비합니다. 키 검증을 자동으로 건너뛰지 않습니다.
- 연결 시 원격 사용자의 `~/.otter-v2-remote`에 실행부를 설치합니다. 다른 전용 절대 경로를
  지정할 수도 있습니다. 인증 파일을 앱으로 복사하지 않고, 통신은 SSH 표준입출력 안에서 수행합니다.
- 등록만으로 실행 수를 예약하지 않습니다. 접속 상태를 먼저 확인하고 실제 시작 직전에
  전체 한도에서 예약합니다. 연결만 끊으면 서버 작업이 계속될 수 있어 예약을 유지합니다.
- **업무 중단·예약 반환**은 확인창을 거쳐 실행부를 중단하고, 종료가 확인된 경우에만
  예약을 반환합니다. 실패/응답 유실 시 예약을 유지하며 종료 기록과 프로세스 상태를 다시 확인합니다.
- **연결 설정 수정**에서 주소·인증 경로·표시 이름을 수정합니다. 실행 수는 안전하게
  중단한 뒤 변경합니다. 이미 연결한 데이터 폴더의 위치/종류는 변경하지 않으며,
  바뀐 SSH 주소도 기존 실행부 ID와 일치해야 합니다. 다른 데이터는 새 환경으로 등록합니다.
- 앱 완전 종료는 로컬·WSL을 중단하고 SSH 작업은 유지하는 구조입니다. 실제 Windows/WSL의
  종료·재연결은 미검증입니다. 소스 버전이 다르면 실행 중인 작업을 자동 교체하지 않습니다.
  기존 실행부를 중단·예약 반환한 후 다시 연결하면 같은 데이터에 최신 실행부를 설치합니다.
- 원격 작업 기록은 해당 실행부에 저장하고, 앱에는 조회한 상태의 캐시를 둡니다.
  오프라인 상태는 업무 실패나 완료로 표시하지 않습니다.

검증 범위: Linux의 임시 SSH 서버에서 설치/저장소/재연결 및 실제 Codex 단일 파일 작업 통과.
검사 서버는 같은 호스트의 격리된 루프백 SSH 서버입니다. 다른 실제 서버나 macOS/Windows
조합까지 수용 검사를 마쳤다는 의미는 아닙니다.

## 검증

### 응답을 놓친 로컬·원격 요청 복구

화면에서 보내는 로컬 변경 요청과 원격 변경 요청은 실행/전달 전에 로컬 실행부 DB에
요청 ID·대상 실행부·원래 본문을 기록합니다. 로컬 접수 ID와 복구 기록은 함께 저장합니다.
응답을 확인하지 못하면 **요청 복구**에 남고, 화면을 새로고침하거나 앱을 재실행해도 유지됩니다.
로컬의 처리 응답이 있으면 바로 결과 요약을 표시합니다. 원격에서 결과를 확인해야 하는 경우
먼저 실행 환경을 연결한 뒤 **처리 결과 조회**를 누르세요. 조회 자체로 업무를 다시 실행하지 않습니다.

- 원격에서 접수 중이면 결과를 기다립니다. 처리 기록이 없는 경우에만 사용자 확인 후
  **동일 요청 다시 전달**을 사용할 수 있습니다. 다른 ID·다른 실행부로 자동 대체하지 않습니다.
- 확인한 응답이 성공이라는 것과 개발 업무가 완료됐다는 것은 다릅니다. 실제 업무·보고를 확인하세요.
- 확인된 생성 요청은 복구 카드에서 해당 프로젝트/업무 대화로 바로 이동할 수 있습니다.
  다른 프로젝트를 보고 있어도 원래 실행 환경과 프로젝트를 확인한 뒤 이동합니다.
- 정상 응답을 화면에서 받으면 자동으로 확인 처리합니다. 응답 유실로 남은 항목은 확인 후 닫습니다.
  복구 목록을 닫아도 로컬·원격 업무/파일은 취소·삭제하지 않습니다.
- 확인 시 전달 기록의 본문과 응답 사본을 비우고 중복 방지용 ID·해시·대상 정보는 유지합니다.
  이는 DB의 보안 삭제 보장이 아니며 원래 업무/대화/처리 기록은 별도로 보존합니다.
- 로컬·원격에서 접수한 뒤 실행부가 중단되어 결과가 없는 요청은 임의로 재실행하지 않습니다.
  연결/실제 변경 결과를 확인해야 하며 이 경우의 자동 부분 복구는 아직 제공하지 않습니다.
- 같은 내용의 미확인 요청을 새 ID로 보내면 차단합니다. 원래 ID로 보낸 로컬 요청은 이미 저장한
  응답만 반환합니다. 응답을 확인한 뒤 같은 내용을 새 업무로 보내는 것은 새로운 요청입니다.
  초안에 내용이 남아 있다는 이유만으로 미접수라고 판단하거나 다시 보내지 마세요.
- 접수 기록은 이 기능 도입 이후 요청 ID가 있는 변경 요청에 적용합니다. 실행 환경의
  연결·연결 해제·중단·접속 설정 변경은 기존 환경 관리 절차를 사용하며 이 복구 목록에 넣지 않습니다.

### 업무 실행 실패 재시도

설정 → 실행 한도에서 자동 재시도 횟수를 지정합니다(기본 2회, 0이면 끔).
새 요청과 사용자 추가 요청부터 로컬·원격에 적용하며, 이미 실행한 업무의 한도는 바꾸지 않습니다.
Codex의 실패 턴과 실행 프로세스 종료가 확인되고, 명령·도구 실행이 관찰되지 않은
일시적 통신/서버 오류만 간격을 늘려 재시도합니다. 같은 대화·작업 브랜치·문서 스냅샷을 유지합니다.
업무 카드에서 예약 횟수·다음 실행 시각을 확인하거나 대기 중 중단할 수 있습니다.
한도 초과, 인증/샌드박스 오류, 연결 유실, 명령 실행 이후의 실패는 자동 재실행하지 않습니다.
종료가 확인된 실패 업무는 대화에서 추가 지시로 이어갈 수 있으며, 기존 파일과 오류 보고는 보존합니다.

### 완료 방식과 별도 검증

설정 → **이 프로젝트의 완료 방식**에서 수동 검토 또는 지정 검증 후 자동 완료를 선택합니다.
검증 이름·실행 파일·인수·제한 시간을 입력하고 실행에 동의해야 합니다. 인수는 한 줄에 하나씩
입력하며 문자열을 자동으로 셸 명령으로 해석하지 않습니다. 최대 8개, 각 1~600초입니다.
직원이 임의로 검증 정책을 변경하지 못하며 저장된 정책은 새 요청/사용자 추가 지시부터 적용합니다.

Otter는 최종 결과 커밋을 별도 작업 공간으로 가져와 모델 호출 없이 Codex의 샌드박스 명령 실행으로
검증합니다. PM 업무는 하위 업무마다 전체 검사를 반복하지 않고 인계가 끝난 최종 결과를 검사합니다.
지정 명령이 모두 종료 코드 0이고 검증 중 추적 파일·원래 작업 결과가 바뀌지 않은 경우만 통과합니다.
자동 완료는 기본 브랜치 병합·푸시·배포가 아닙니다. 수동 방식은 검사가 통과해도 사용자 검토를 기다립니다.

- 수동 **검토 완료**는 확인창에 고정한 실행 회차·변경 번호·결과 커밋과 별도 검증 결과를 확인하고
  **확인한 결과를 완료 처리** 버튼으로 처리합니다. 별도 확인 체크박스는 없습니다. 창을 열어 둔 동안 결과가 바뀌면 최신 보고를 확인한 뒤 다시 열어야 합니다.
  이전 화면이나 다음 실행 전의 승인은 새 결과에 적용되지 않습니다. 검증 실패/미검증 기록을 통과로 바꾸지 않습니다.
  완료 기록에는 사용자가 승인한 결과의 변경 번호·실행 회차·커밋이 남으며, 추가 요청에는 새 검토가 필요합니다.
- 업무·보고에서 검증 커밋, 실행 명령, 종료 코드, 실패/미실행 항목을 따로 확인합니다.
- 검증 공간에는 커밋된 파일만 있습니다. 필요한 의존성/도구는 별도로 준비해야 하며 네트워크를
  자동 허용하거나 패키지를 임의 설치하지 않습니다. 지정 검사 통과는 전체 요구사항 충족 보증이 아닙니다.
- 실패/중단/종료 미확인 결과는 자동 완료하지 않습니다. 종료 미확인 시 실행 자리를 반환하지 않으며,
  실행부 재시작 후 미완료 검증을 자동 재실행하지 않습니다. 명령 출력은 자격 증명 노출을 줄이기 위해 저장하지 않습니다.
- 현재 검사 호스트는 `bwrap` 격리 초기화를 차단하여 실제 Codex 검증 명령은 실행하지 못했습니다.
  보호를 끄는 대체 실행은 없으며 macOS/Windows/WSL 및 지원 서버에서 실제 검증 성공을 확인해야 합니다.

### 아이디어에서 시작

프로젝트 시작 → **아이디어부터**에서 아이디어와 PM의 역할·모델·필요 이유를 확인합니다.
**PM 배정하고 회의실 열기**로 준비합니다. 별도 확인 체크박스나 자동 모델 실행은 없습니다.
회의실에서 **PM에게 아이디어 전달**로 실제 인터뷰를 시작하고, 같은 대화에 답변합니다.
PM의 문서·채용 제안은 승인 전 반영되지 않습니다. 네 문서와 팀을 확인한 뒤 폴더 탐색으로
새 저장소의 위치를 확정합니다. 인터뷰 기록은 유지되며 개발은 새 업무로 요청합니다.
**저장 위치 확정·개발 공간 열기** 버튼이 문서·팀 확인과 전환 요청을 함께 처리합니다.
회의실에 저장하지 않은 편집이 있으면 개발 공간으로 전환하지 않습니다.

인터뷰는 쓰기/네트워크를 허용하지 않는 제한 읽기 권한 프로필을 사용합니다.
현재 검사 호스트에서는 Codex의 파일 접근 샌드박스 초기화가 거부되어 **실제 모델을 통한
아이디어 전체 흐름은 미검증**입니다. 보호를 끄거나 전체 읽기로 대체하지 않습니다.
GUI와 합성 제공자 검사는 통과했지만, 지원되는 실행 환경에서 실제 Codex 수용 검사가 필요합니다.

### 코드가 필요할 때 외부 IDE 열기

프로젝트 상단의 **외부 IDE에서 열기**는 원본 저장소를, 업무 카드의 **작업 폴더 IDE로 열기**는
해당 직원의 격리된 작업 폴더를 선택합니다. 실제 Git 경로·현재 브랜치·진행 업무를 확인하며,
다른 프로젝트/저장소로 바뀐 작업 폴더와 링크로 대체된 경로는 거부합니다.
원본을 여는 것만으로 직원의 결과가 병합되지는 않습니다.

- 설치형 앱에는 VS Code 연결을 구현했습니다. 설치 위치를 찾지 못하면 네이티브 파일 선택기로
  실행 파일을 고릅니다. macOS는 `Visual Studio Code.app`, Windows는 `Code.exe`, Linux는 `code`
  실행 파일을 선택합니다. 다시 선택 옵션도 제공합니다. 최종 대상 확인 후에만 실행 요청을 보냅니다.
- SSH는 VS Code의 Remote - SSH에 **같은 대상·사용자·포트·키**를 등록한 Host 별칭이 필요합니다.
  Otter 접속 성공이 IDE 접속 성공까지 보증하지는 않습니다. SSH 설정/인증 파일을 자동 복사하거나
  수정하지 않으며 연결이 끊기면 로컬 폴더로 대체하지 않습니다.
- WSL은 Windows의 VS Code와 WSL 확장을 사용하며 등록한 배포판을 명시합니다.
- 브라우저에서는 검증한 경로를 복사해 해당 환경의 IDE에서 엽니다. 복사 권한이 없으면
  경로 입력란을 선택해 직접 복사할 수 있습니다. 표시하는 argv는 붙여넣을 셸 명령문이 아닙니다.
- 외부 IDE 편집은 실제 파일에 영향을 줍니다. Otter는 IDE 열기로 직원을 자동 중단하거나
  커밋·병합·푸시하지 않습니다. 동시 편집 전에는 업무 상태를 확인하세요.

연결 인자는 [VS Code 공식 CLI 문서](https://code.visualstudio.com/docs/configure/command-line)의
로컬 폴더/`--remote` 형식을 사용하며 셸 문자열로 합치지 않습니다. [Remote - SSH 설정](https://code.visualstudio.com/docs/remote/ssh)과
IDE의 확장·작업공간 신뢰·원격 서버 설치는 VS Code 측에서 별도로 확인해야 합니다.
현재 검증 머신에서는 Electron 실행에 필요한 `libgtk-3.so.0`이 없어 **실제 네이티브 앱과
VS Code 창 열기는 미검증**입니다. 경로/인자 전달·접근 제한·브라우저 검사는 통과했으며,
macOS/Windows/WSL 실기기 검증이 추가로 필요합니다.

### 직원 결과를 원본에 반영

업무 카드의 **검토 완료**는 결과 확인창을 엽니다. 확인한 결과를 완료 처리하면 별도로 설정한 자동 반영이 시작될 수 있습니다.
기본 수동 설정에서 **원본에 반영…**은 실제 원본 파일과 브랜치를
변경하는 별도 동작입니다. 최종 업무가 검토 요청/완료 상태이고 프로젝트의 실행이 끝나면 사용할 수 있습니다.
PM이 배정한 하위 업무는 PM의 최종 결과를 통해 반영합니다.

- 실행 환경·원본 폴더·브랜치·변경 파일을 확인하고 승인합니다. 등록 당시 원본 브랜치가 대상이며
  다른 브랜치로 자동 전환하지 않습니다. 확인 뒤 커밋이나 업무가 바뀌면 새 확인을 요구합니다.
- 원본/직원 폴더에 커밋하지 않은 변경이 있거나 충돌이 예상되면 중단합니다. 사용자 변경을
  임의로 커밋·stash·삭제하지 않습니다. 충돌은 직원에게 원본 변경을 작업 브랜치에 통합하도록 요청하세요.
- 원본에 이미 추가된 다른 커밋도 유지하는 병합 커밋을 만듭니다. 승인한 두 커밋과 사전 검사한
  트리를 고정하며, 원본 반영 때 Git 훅·자동 stash를 실행하거나 ignored 파일을 덮어쓰지 않습니다.
- 원격 프로젝트는 선택한 실행부에서 반영합니다. 연결 실패 시 로컬로 대체하지 않습니다.
- 결과는 별도 Git 반영 보고에 남습니다. 병합 결과의 추가 테스트·푸시·배포는 하지 않습니다.
  이미 반영된 결과는 다시 병합하지 않으며 같은 요청 ID의 재전송도 중복 처리하지 않습니다.
  별도 자동 푸시 설정이 있으면 수동 반영을 마친 완료 업무가 자동 푸시로 이어질 수 있습니다.

Git 2.38 이상이 필요합니다. 사용자 정의 병합 드라이버/파일 필터가 설정된 저장소는 현재
외부 IDE에서 반영해야 합니다. 원본 반영 중에는 외부 IDE/터미널에서 저장소를 동시에 수정하지 마세요.
반영 도중 오류·중단으로 결과를 확정하지 못하면 커밋 ID를 보존하고 재실행하지 않습니다.
이 불확정 상태는 업무 카드의 **실제 Git 결과 대조**에서 확인합니다. 증거가 충분할 때만 기록을 복원합니다.
이는 전체 에이전트 명령의 Git/배포 권한 정책 강제가 완료되었다는 뜻이 아닙니다.

### 완료 후 자동 반영

설정 → **완료 후 자동 반영**에서 원본 반영·원격 푸시·배포 명령을 각각 수동/자동으로 선택합니다.
기본값은 모두 수동입니다. 실행 폴더·원본 브랜치와 실제 푸시 주소·대상 브랜치를 확인하고
승인해야 저장됩니다. 자동 푸시는 기존 커밋 이력 전송 및 원격 CI/CD·배포·유료 자동화 가능성도
별도로 확인받습니다. 자동 배포에는 명령/인수·향후 원본 커밋에서의 실행 및 외부 변경·반복 실행·비용
영향에 대한 추가 동의가 필요합니다. 설정 미리보기나 저장만으로 Git 반영·전송·배포를 수행하지 않습니다.

- 설정 후 새로 받은 최종 업무에 적용합니다. 기존 업무에는 소급하지 않고 PM 하위 업무는 직접 반영하지 않습니다.
- 수동 완료 방식이면 사용자 검토 승인을 먼저 기다리고, 자동 완료 방식이면 지정 검증을 통과해야 합니다.
  다른 업무가 진행 중이거나 실행/Git 종료를 확인하지 못한 프로젝트는 기다립니다.
- 원본 반영만 수동·푸시만 자동으로 조합할 수 있습니다. 이때 완료 업무를 수동 반영하면 자동 푸시합니다.
- 배포는 완료 업무의 원본 반영을 기다립니다. 자동 푸시도 선택했다면 푸시 확인 후 배포하며,
  푸시가 막히면 배포하지 않습니다. 수동 반영·수동 푸시·자동 배포 조합에서는 수동 반영 후 푸시 없이 배포합니다.
- 설정한 배포 실행 파일의 실제 경로·내용 해시를 고정하며 실행 전 변경됐으면 멈춥니다.
  같은 정책과 원본 커밋의 명령 정상 종료 기록이 있으면 중복 실행하지 않습니다.
  다른 커밋/새 정책에서는 반복 실행될 수 있으며, 배포 명령 자체의 외부 효과와 비용도 승인 범위에 포함됩니다.
- 배포는 원본 브랜치의 현재 커밋을 대상으로 합니다. 해당 업무 외에 원본에 이미 반영된 내용도 포함합니다.
  향후 바뀐 스크립트·의존성·설정을 호스트 계정 권한으로 실행하므로 아래 수동 배포의 실행 경계를 함께 확인하세요.
- 승인한 주소·원본 브랜치를 고정합니다. 주소 변경, 미커밋 변경, 충돌, 실패는 확인 필요로 보고하고
  자동 재시도하지 않습니다. 업무에서 실제 Git 결과를 확인하고 수동으로 마무리하세요.
- 설정 변경/해제는 이전 설정으로 받은 업무의 추가 자동 반영도 중단합니다. 이미 시작된 Git/배포 명령을
  되돌리지는 않으며 앱 종료도 그 결과 기록까지 기다립니다. 실행부 재시작 시 미완료 자동 반영을 재실행하지 않습니다.
- 설정 승인/해제 및 업무별 결과는 별도 보고로 남습니다. 푸시 성공이 원격 CI/CD 성공을 의미하지는 않습니다.
- 배포 명령 종료 코드 0도 서비스 배포 성공을 의미하지는 않습니다. 실패한 업무의 자동 배포는
  결과 확인 후에도 다시 실행하지 않습니다. 자동 설정이 남아 있으면 이후 새 업무에는 계속 적용됩니다.

로컬·원격 모두 해당 실행부에서 처리합니다. 에이전트 임의 명령의 권한 강제는 아직 미완료이며,
이 옵션이 직원의 모든 명령을 포괄적으로 허용하지는 않습니다.

### 수동 배포 명령

프로젝트 상단 **배포…**에서 실행 환경에 설치된 도구의 절대 경로와 인수를 나눠 입력합니다.
원본 브랜치의 커밋을 대상으로 하며 직원 결과는 먼저 원본에 반영하세요. 명령·폴더·커밋을
확인한 다음, 실행 계정의 파일/네트워크/인증 정보 접근 및 외부 변경·비용 영향에 별도로 동의해야 실행합니다.
이 화면은 일회성 수동 실행입니다. 자동 배포는 위의 프로젝트 설정에서 별도 승인합니다.

- 셸 명령문을 자동 해석하지 않고 실행 파일과 argv로 전달합니다. 실제 실행 파일의 경로·내용 해시,
  명령·커밋·프로젝트 상태를 실행 전에 다시 대조합니다. 확인 후 바뀌면 재승인이 필요합니다.
- 이 명령은 **실행 계정의 호스트 권한**으로 실행되며 Codex 샌드박스에 제한되지 않습니다.
  스크립트·의존성·ignored 설정 파일·기존 로그인에 따라 영향이 달라질 수 있으므로 신뢰하는 명령만 실행하세요.
  승인한 커밋이 의존성/환경 설정/외부 서비스 상태까지 고정한다는 뜻은 아닙니다.
- 배포 명령/인수는 로컬 기록과 보고에 저장합니다. 비밀번호·토큰을 인수로 넣지 마세요.
  표준 출력/오류는 인증 정보 노출을 막기 위해 수집·표시하지 않습니다. 결과는 배포 서비스에서 확인하세요.
- 정상 종료 코드 0은 **명령 종료**로 표시하며 서비스 배포 성공으로 표시하지 않습니다.
  실패·시간 초과·재시작은 결과 확인 필요로 두고 자동 재시도하지 않습니다.
- Linux/macOS 실행부의 새 배포는 별도 프로세스 그룹에서 실행합니다. 상위 명령이 종료돼도 같은 그룹이
  남아 있거나 조회 결과를 확정하지 못하면 정상 종료 코드 0을 미확정으로 처리합니다.
  그룹 부재를 확인하기 전에는 사용자 확인 메모로 제한을 해제하거나 앱을 완전 종료할 수 없습니다.
  후속 프로세스가 끝난 뒤 확인/종료를 다시 시도하세요. 한 번 확인한 그룹 부재는 기록에 보존합니다.
  Windows 네이티브 및 이전 기록은 상위 명령 관찰 범위이며, 별도 세션·외부 서비스로 분리된 작업까지
  추적하는 기능은 아닙니다. 번호 재사용/조회 권한/회수되지 않은 프로세스 때문에 미확정이 유지될 수 있으므로
  표시된 번호만 보고 다른 프로세스를 임의로 종료하지 마세요.
- 불확정 상태에서는 새 업무/Git 반영/배포를 막습니다. 원 명령 종료를 확인할 수 있을 때만
  사용자가 후속 프로세스와 외부 서비스 결과를 확인한 메모를 남겨 제한을 해제할 수 있습니다.
  이 기록은 사용자 확인이며 Otter의 서비스 검증이나 재배포가 아닙니다. 다음 수동 배포에는 중복 효과 동의를 다시 받습니다.
  프로젝트의 자동 배포 설정이 남아 있으면 새 업무는 사전 승인한 정책을 따르므로 원치 않으면 설정을 해제하세요.
- 명령은 포그라운드에서 최종 결과까지 기다리는 형태여야 합니다. 제한 시간(1~600초)에는 원 명령에
  종료를 요청하고 실제 종료까지 실행 자리를 유지합니다. 분리된 후속 프로세스/외부 비동기 처리의 취소는 보장하지 않습니다.
- 대화상자를 닫아도 실행부에서 진행하며 배포 메뉴와 보고에서 결과를 확인합니다. 앱 완전 종료는
  접수한 명령의 결과 기록을 기다립니다. 현재 프리뷰는 모든 하위 프로세스의 생명주기를 격리하는 실행기가 아닙니다.

그룹 관찰은 [Node의 프로세스 그룹 생성](https://nodejs.org/api/child_process.html#optionsdetached)과
[POSIX 프로세스 그룹 존재 확인](https://man7.org/linux/man-pages/man2/kill.2.html)을 사용합니다.
저장된 그룹 번호로 종료 신호를 보내지는 않습니다.

### 원격 저장소로 푸시

프로젝트 상단의 **Git 푸시…**에서 등록된 Git 원격과 대상 브랜치를 선택합니다.
**원격 상태와 전송 내용 확인**은 조회만 수행하며, 전송 커밋과 주소를 확인하고 승인해야 푸시합니다.
원본 브랜치의 커밋 이력이 전송 대상입니다. 직원 결과는 먼저 원본에 반영하세요.

- 푸시 주소와 조회 주소가 다르면 실제 푸시 주소를 사용합니다. 단일 주소·단일 브랜치만 전송하고
  태그/다른 브랜치/하위 모듈을 함께 보내거나 원격 브랜치를 삭제하지 않습니다.
- 원격 이력을 유지하는 추가 전송만 허용합니다. 원격 변경이 원본에 없거나 조회되지 않았으면
  외부 IDE에서 fetch와 변경 통합 후 다시 확인하세요. 확인 후 원본/원격이 바뀌면 재승인이 필요합니다.
- 서버의 **CI/CD·자동 배포·유료 작업이 실행될 수 있음**을 확인받습니다. 푸시 성공과 원격 자동화의
  성공은 구분하며, 전송을 확인하면 별도 보고를 남깁니다.
- 로컬 pre-push 훅은 실행하지 않습니다. Git LFS 등 훅이 필요한 저장소는 현재 외부 IDE를 사용하세요.
  서명된 푸시, 사용자 정의 원격 도우미, 다중 푸시 주소, 주소를 거듭 바꾸는 재작성 설정은 지원하지 않습니다.
- 인증 정보를 주소에 직접 포함하지 않는 SSH/HTTPS 또는 로컬 절대 경로를 지원합니다. 선택한 실행 환경의
  기존 Git 인증을 사용합니다. 비밀번호/토큰/쿼리 문자열을 넣은 주소는 거부하며 원격 설정을 자동 변경하지 않습니다.
- 응답 유실/오류로 결과가 불확정하면 전송 커밋과 대상을 보존하고 재전송하지 않습니다.
  **실제 Git 결과 대조**에서 원래 원격과 실행 기록을 확인하세요. 전체 권한 정책 강제는 진행 중입니다.

내부적으로 [명시적 기대 커밋을 쓰는 Git lease](https://git-scm.com/docs/git-push)를 사용하되,
그 전에 원격 커밋이 전송 커밋의 조상인지 검사해 이력을 덮어쓰는 푸시를 금지합니다.
조회/전송 도중 외부 IDE나 터미널에서 원본과 Git 접속 설정을 동시에 변경하지 마세요.

### 병합·푸시 결과 대조와 복구

업무 카드와 Git 푸시 화면에 미확인 실행의 **실제 Git 결과 대조**를 제공합니다.
조회만으로 기록을 변경하거나 병합/푸시를 다시 실행하지 않습니다. 원격의 후속 이력을 확인할 때는
Git 객체를 가져올 수 있지만 작업 파일·브랜치·태그·`FETCH_HEAD`를 변경하지 않습니다.

- 실행 종료와 결과 커밋의 원본/원래 원격 이력 포함이 확인되면 **반영 기록 복원**을 승인할 수 있습니다.
  이후 커밋이나 되돌리기가 있을 수 있으며 과거 결과의 존재가 현재 파일이나 CI/CD 성공을 보장하지는 않습니다.
- 로컬 Git 종료·변경 전 브랜치·깨끗한 작업 폴더·진행 중 Git 작업 없음이 확인되거나,
  Git의 명시적 원격 전송 거부와 종료가 확인되면 **미반영으로 기록**할 수 있습니다.
  원인을 해결한 후 병합/푸시는 새로 확인하고 승인해야 합니다.
- 실행 PID가 아직 존재하거나 종료 기록이 부족하면 미확인을 유지합니다. 원격 브랜치 부재,
  네트워크 오류만으로 미전송을 단정하지 않습니다. 현재 원격 이름의 설정을 바꿨어도 원래 전송 주소를 대조합니다.
- 조회 뒤 Git 상태/실행 기록이 바뀌면 다시 대조합니다. 복구는 별도 보고에 남고 요청 ID 재전송은 중복 복원하지 않습니다.
- 미확인 Git 실행이 있는 프로젝트에서는 새 업무·다른 병합/푸시·지침 파일 연결을 시작하지 않습니다.
  기존 대기 업무도 실행하지 않으며, 결과를 정리한 뒤 원래 승인한 대기 업무는 재개될 수 있습니다.

이전 버전의 종료/PID 증거가 없는 기록, PID가 재사용되어 여전히 존재하는 경우,
원격 이력이 사라졌거나 서버가 처리를 계속하는지 알 수 없는 경우는 자동으로 해제하지 않습니다.
임의의 실패 판정이나 강제 복구 대신 원래 실행 환경과 원격 서비스의 확인이 필요합니다.

### 직원 설정 재사용과 변경 충돌

직원 화면의 **프로젝트 설정**은 해당 배정만, **원본 편집**은 재사용할 라이브러리 설정만 바꿉니다.
이미 배정된 다른 프로젝트나 접수된 업무의 설정을 자동으로 덮어쓰지 않습니다.
**원본과 비교 / 기반 직원과 비교**에서 가져올 항목을 선택하며, 창을 열 때 확인한 원본·대상 버전을 검사합니다.
그사이에 설정이 바뀌면 반영을 거절합니다. **최신 설정 다시 비교**로 갱신하고 항목을 다시 선택하세요.
직접 편집·파생 생성 중 충돌이 나도 입력은 유지됩니다. 작성한 내용을 복사한 뒤 창을 닫고 다시 열어
최신 설정과 조정하세요. 새로고침·창 닫기 이후 직원 편집 초안 복원은 아직 지원하지 않습니다.
원격 배정에도 같은 비교 검사를 적용하며, 구버전 실행부는 업데이트 후 사용해야 합니다.

### 업무 찾기

업무 화면에서 제목·담당 직원 검색과 담당/상태 필터를 함께 사용할 수 있습니다.
진행 중 / 확인할 업무 / 완료·인계로 구분하며, 실패·중단·종료 미확인·답변/승인 대기를
**확인할 업무**에서 모아 봅니다. 알 수 없는 상태도 숨기지 않습니다.
대화를 열었다 업무 화면으로 돌아오면 검색 조건을 유지합니다. 다른 프로젝트에는 조건을 적용하지 않으며,
새로고침 이후의 필터 저장은 지원하지 않습니다. 연결이 끊기면 마지막 조회 결과임을 표시합니다.

### 작업 중인 직원에게 추가 지시

업무 대화에서 실행 중인 업무를 선택하고 **현재 실행에 추가 지시 보내기**를 사용합니다.
같은 업무·작업 폴더·현재 실행에 내용을 추가하며 별도 업무를 만들지 않습니다.
대기/준비·질문/승인·마무리 단계에서는 접수를 거절할 수 있습니다. 새 업무를 맡기려면
**모든 업무 대화**를 선택하세요. 이미 실행한 작업 취소나 권한 승인을 대신하지 않습니다.

- 전달 확인 중 / 전달됨 / 제공자 접수 거절 / 전달 여부 미확인을 구분합니다.
- 전달됨은 제공자의 접수 확인이며, 요청을 실제로 구현·검증했다는 뜻은 아닙니다.
- 실행 회차나 현재 실행 ID가 바뀌면 보내지 않습니다. 거절된 HTTP 요청의 초안은 유지합니다.
- 제공자에 전송한 뒤 결과가 불확실하면 내용을 대화에 보존하고 해당 실행에 추가 전송을 막습니다.
  자동 재전송하거나 다음 업무의 입력에 다시 넣지 않습니다. 직원 응답과 결과를 먼저 확인하세요.
- 같은 요청 ID의 재전달은 기존 처리 결과만 조회합니다. 앱 재시작도 추가 지시를 자동 전송하지 않습니다.
- 원격도 대상 실행부가 이 기능을 지원해야 합니다. 현재 구현은 텍스트 지시만 지원하며 모델·권한 설정은 바꾸지 않습니다.

[공식 App Server 규격](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)의 `turn/steer`를 사용합니다.
제공자 대역과 설치된 Codex 0.153.4의 생성 규격을 검증했으며, 실제 모델 수용 검증은 별도입니다.

### 중단한 업무 재개

업무 카드에서 **대화 열기**로 들어가 재개할 내용을 입력하고 **이어서 진행** 버튼 또는 Enter로 요청합니다.
별도 확인 체크박스는 없습니다. Otter가 종료를 확인한 중단 업무만 가능하며, 앱을 다시 켜는 것만으로 자동 재개하지 않습니다.
같은 업무·대화·작업 폴더를 유지하고 현재 직원 설정/지침을 적용합니다. 이미 실행한 명령이나 외부 효과를 되돌리지는 않습니다.
요청 도중 업무 상태가 바뀌면 요청을 거절하고 최신 상태를 보여줍니다. 내용을 확인한 뒤 다시 전송해야 합니다. 후속 실행 전에 작업 폴더의 저장소·경로·브랜치를 검사하며,
바뀐 브랜치를 자동 전환하거나 보존한 파일을 지우지 않습니다. 지침의 외부 수정 충돌도 기존 검사로 보호합니다.

강제 종료/실행부 유실이나 이전 버전처럼 종료 확인 기록이 없는 업무는 바로 재개하지 않습니다. 기존 실행과 작업 파일을
먼저 확인해야 하며, 아직 이를 자동 판정하거나 강제로 재개하는 기능은 없습니다. PM이 배정한 하위 업무는 상위 PM에서
진행 방법을 정합니다. 하위 실행의 종료가 미확인이면 PM 재개도 막으며, PM을 재개한다고 중단된 하위 업무를 자동 재실행하지 않습니다.
이 기능은 새로 받은 재개 요청을 같은 작업 맥락에서 실행하는 흐름이며, OS 전원 차단 복원이나 백업 파일 복원은 아닙니다.

### 작성 중인 문서와 대화

문서 편집과 대화 입력은 프로젝트·직원·대화별 초안으로 구분합니다. 메뉴/프로젝트를 옮겼다가
돌아오거나 **같은 탭에서 새로고침**해도 복원합니다. 업무 선택 목록에는 초안이 있는 대화를 표시합니다.
문서는 저장, 대화는 보내기를 눌러야 반영 요청하며 초안을 직원에게 자동 전달하지 않습니다.
응답을 기다리는 중 추가한 입력은 지우지 않고, 문서 기준 버전이 바뀌면 기존 충돌 확인을 유지합니다.
아이디어 회의실에서도 저장하지 않은 문서 초안이 남아 있으면 개발 공간 전환을 막습니다.

초안은 이 브라우저 탭의 `sessionStorage`에 보관됩니다. **탭/앱 완전 종료·실행 주소 변경 뒤의
복구나 다른 기기 동기화는 보장하지 않습니다.** 저장소 용량/접근 오류가 나면 알리고 현재 화면의
메모리 초안은 유지합니다. 오류 상태에서 새로고침·종료하기 전 내용을 복사해 주세요.
초안 버리기는 확인 후 해당 사본만 지웁니다. 이미 접수된 요청·업무·저장된 문서는 취소하거나 삭제하지 않습니다.
로컬·원격 전송 결과가 불명확하면 먼저 요청 복구에서 결과를 확인하세요.

### 저장소 지침

프로젝트 지침은 등록 시 루트의 `AGENTS.override.md`, `AGENTS.md` 순서로 발견합니다.
문서 화면의 **저장소 지침 파일**에서 비교한 뒤 가져오거나 원본에 반영합니다.
Otter 문서 저장/직원 제안 승인만으로 원본 파일을 변경하지 않습니다. 원본 반영 시 이전 파일을
Git 내부 `otter-instruction-backups`에 보존하며, 비교 이후 외부에서 변경된 파일은 다시 비교해야 합니다.
연결한 문서의 스냅샷은 새 업무/대화 재개 시 작업 브랜치에 적용하되, 해당 브랜치에서 따로 수정한
지침은 자동 교체하지 않습니다. 하위 폴더 지침과 사용자 지정 fallback 파일의 동기화는 지원하지 않습니다.

### 승인한 노하우 재사용

**문서·지침 → 회사 공유 지식**에서 필요한 경우에만 펼쳐 사용합니다. 직원에게 공유할 노하우를
제안해 달라고 요청하거나 직접 작성할 수 있습니다. 같은 회사의 다른 프로젝트/실행 환경에서
재사용할 본문인지 확인하고 공유를 승인해야 라이브러리에 남습니다.

- 공유 승인은 다른 프로젝트의 지침에 자동 적용한다는 뜻이 아닙니다. 사용자가 선택해서
  가져온 본문만 프로젝트 문서 사본이 되고 새 업무·대화 재개부터 적용됩니다.
- 원래 대화·소스·파일 경로를 자동 첨부하지 않습니다. 알려진 일부 자격 증명 형식은 차단하지만,
  기밀·고객 정보 전체를 자동 판별하지는 못하므로 승인 전에 본문을 확인해야 합니다.
- 사본을 편집해도 공유 원본이나 다른 프로젝트는 바뀌지 않습니다. 다시 가져오기로 사본을
  덮어쓰지 않습니다. 다른 회사로의 가져오기는 지원하지 않습니다.
- **공유 중지**는 새로운 적용을 막습니다. 이미 가져간 문서와 실행 기록은 삭제하지 않으므로
  필요하면 각 프로젝트 문서를 직접 수정하세요. 승인 본문을 고치려면 새 지식으로 다시 공유합니다.
- 원격의 승인된 본문은 앱의 회사 라이브러리에 보관되고, 선택한 대상 실행 환경으로 전달됩니다.
  공유 성공 뒤 상태 조회가 끊겨도 확인된 본문은 유지하며, 오래된 상태가 공유 중지를 되돌리지 않습니다.

```bash
pnpm check
pnpm test
pnpm build
node scripts/smoke-v2-ui.mjs
node scripts/smoke-v2-ideas.mjs
node scripts/smoke-v2-verification.mjs
node scripts/smoke-v2-recovery.mjs
node scripts/smoke-v2-drafts.mjs
node scripts/smoke-v2-editor.mjs
```

UI 검사는 Playwright Chromium 설치가 필요합니다. 브라우저 캐시가 별도 경로라면
`PLAYWRIGHT_BROWSERS_PATH`를 지정하세요.

Linux의 실제 배포 후속 프로세스 검사는 `python3`가 필요합니다. 검사 자식 프로세스에만 Linux
subreaper를 설정해 고아 프로세스를 회수하며, 제품 실행·설치 패키지에는 Python 의존성이 없습니다.

격리된 로컬 SSH 검사(OpenSSH 서버 필요, 임시 키 사용, 모델 사용량 없음):

```bash
node scripts/smoke-v2-ssh.mjs --run
```

검사 키·설정은 무시 경로 `.otter-dev/ssh-smoke-*`에만 생성합니다. 개인 SSH 설정과 키를
수정하지 않으며, 검사 후 임시 서버와 실행부를 종료합니다.

다음 검사는 **기존 Codex 계정의 사용량을 소비**하며, 자동 테스트에 포함하지 않습니다.
임시 저장소의 단일 파일 변경만 확인해서 승인합니다. 임시 파일과 검사 기록은 보존합니다.

```bash
node scripts/smoke-v2-codex.mjs --run
node scripts/smoke-v2-codex.mjs --run --pm
node scripts/smoke-v2-codex.mjs --run --idea
node scripts/smoke-v2-ssh.mjs --run --codex
```

## 데이터와 보존

- Node 실행부의 기본 데이터 경로: `~/.otter-v2`. `OTTER_V2_DATA`로 변경합니다.
- 개발 포트: `OTTER_V2_PORT`로 변경합니다. 실행부는 127.0.0.1에만 바인딩합니다.
- 설치형 데이터: Electron 사용자 데이터 폴더 아래 `v2`.
- 실행부가 비정상 종료되면 잠금 파일과 기존 프로세스를 확인해야 합니다.
  기존 작업이 살아 있을 수 있으므로 잠금을 자동 삭제하거나 업무를 자동 재실행하지 않습니다.
- 시작 도중 DB 읽기/초기화가 실패하면 생성자 연결과 이번 시작에서 만든 잠금만 정리합니다.
  원본 DB를 빈 파일로 바꾸거나 손상된 내용을 자동 삭제하지 않습니다. 설치 앱은 확인할 기록 위치를,
  개발 실행은 데이터/권한/디스크 확인 안내를 표시하며 원시 DB 내용은 오류 안내에 넣지 않습니다.
