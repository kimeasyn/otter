# Otter MVP 요구사항 정의서 v0.1

작성일: 2026-09-11

상태: 8차 인터뷰를 종합한 요구사항 기준. 이후 사용자의 재구현 시작 요청에 따라 구현 중이다.
세부 제안 기본값과 미검증 항목은 아래에서 구분한다. 진행 증거는 [구현 기록](IMPLEMENTATION_V2.md)에 남긴다.

근거: [요구사항 인터뷰 및 결정 기록](REQUIREMENTS_V2.md), 사용자 제공 컨셉 이미지 3장.

## 1. 제품 정의

> 사람 한 명이 AI 직원에게 직접 지시하거나 PM에게 업무를 위임하고,
> 코드 편집 대신 사무실·대화·문서·보고를 통해 개발을 진행하는 설치형 작업공간.

두 컨셉을 함께 유지한다.

- **IDE without code / develop without code**: 프로젝트를 실제로 개발하지만,
  코드의 직접 열람·수정은 우선 외부 IDE에 맡긴다. 목표·지침·대화·실행·검토를 GUI에서 다룬다.
- **Managing visualized agents like company**: 직원·팀·사무실이라는 익숙한 표현으로
  에이전트의 역할, 배정, 협업, 막힘과 결과를 이해하고 조작한다.

첫 사용자는 Codex를 사용하는 개발자인 사용자 본인이다. 회사 업무와 사이드 프로젝트에
실제로 사용한 뒤 같은 니즈의 개발자에게 배포한다. 비개발자의 체계적인 바이브 코딩과
AI 직원 기반 1인 사업 플랫폼을 장기 방향으로 유지한다.

사무실은 단순 장식이 아니며, 제품은 경영 시뮬레이션 게임 자체도 아니다.
화면 속 직원의 활동은 실제 업무와 연결되어야 한다.

## 2. 문서의 승인 구분

- **확정 요구**: 인터뷰에서 사용자가 선택하거나 수용한 제품 요구. 원문 ID는 `R-001`~`R-038`.
- **제안 기본값**: 선택 가능한 기능의 최초 설정이나 상세 동작에 대한 작성자의 제안.
  8절에 모으며, 사용자가 이미 수치를 승인한 것으로 간주하지 않는다.
- **도출된 품질 조건**: 확정 요구가 안전하고 신뢰할 수 있게 동작하기 위한 검증 조건.
- **기술 검증 항목**: 아직 구현 가능 범위나 수단을 확인해야 하는 부분. 지원 완료를 주장하지 않는다.

기존 Otter 코드·PRD는 보존한다. 이전 기능이나 컨셉 이미지의 모든 메뉴를 자동으로
새 MVP의 필수 기능으로 승계하지 않는다. 일정·개발 프레임워크·DB·통신 프로토콜은 미정이다.

## 3. 배포 및 실행 범위

| 항목           | MVP 요구                                               | 별도 확인 사항                                                        |
| -------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| 배포           | macOS/Windows 설치형을 기본 방향으로 한다.             | `.dmg`·`.exe` 등 구체적인 설치 포맷, 서명, 지원 OS/CPU, 업데이트 방식 |
| 로컬 작업      | 파일/폴더 탐색으로 Git 저장소를 선택한다.              | macOS 로컬 및 Windows/WSL 연동. Windows 네이티브 실행 세부 범위       |
| 원격 작업      | SSH 서버의 프로젝트를 선택하고 실제 작업한다.          | 원격 OS, SSH 인증 방식, 실행부 설치·업데이트·접속 복원                |
| 에이전트       | Codex 우선. 사용자가 가진 이용 권한을 활용한다.        | 공식 연동 경로, 인증·동시 실행·세션·권한 승인·사용량 정보의 지원 범위 |
| 사용자         | 사람 한 명이 AI 직원들을 운영한다.                     | 다른 사람에게 각자 설치형으로 배포할 수 있다. 공동 운영은 제외        |
| 창 닫기        | 로컬 백그라운드 작업 유지                              | OS별 닫기/트레이/메뉴 막대 UX                                         |
| 완전 종료      | 진행 중인 로컬 작업을 알리고 종료 확인                 | 중단된 작업의 기록과 안전 처리                                        |
| 원격 지속 실행 | 접속 앱을 종료해도 살아 있는 원격 실행부의 작업은 유지 | UI 재접속 시 상태와 기록 복원. 서버 종료 후 자동 재개는 별도 검토     |

로컬 작업 PC가 꺼지거나 잠들면 로컬 실행 지속은 보장하지 않는다. 원격 지속 실행을
위해 Otter 자체 클라우드나 자체 LLM을 MVP에 구축하지 않는다.

## 4. 사용자가 이해해야 할 개념

아래는 사용자 관점의 용어 정리이며, DB나 클래스 구조의 확정안이 아니다.

| 개념      | 의미와 관계                                                                                          |
| --------- | ---------------------------------------------------------------------------------------------------- |
| 회사      | 프로젝트 하나 또는 여러 프로젝트 묶음. 사용자가 구성 방식을 선택한다.                                |
| 프로젝트  | 목표·저장소·업무·대화·자료의 작업 맥락. 같은 회사 안에서도 프로젝트 기억은 분리한다.                 |
| 직원      | 역할·모델·스킬·지침을 가진 에이전트. 다른 프로젝트에서 재사용하거나 조정한 파생 직원을 만들 수 있다. |
| 팀        | 프로젝트에 배정된 직원들의 협업 구성. PM이 업무를 분담한다.                                          |
| 업무      | 직접 지시 또는 PM 위임으로 만들어진 작업 단위. 담당·진행·질문·결과를 연결한다.                       |
| 대화      | 직원 1:1, 프로젝트 단체방, 업무별 스레드. 실제 직원 간 메시지와 인계도 확인한다.                     |
| 보고      | 대화와 별도로 확인하는 결과·요약·검토 자료. 관련 업무와 연결된다.                                    |
| 실행 환경 | 실제 파일 수정·명령·테스트가 수행되는 로컬 PC, WSL 또는 SSH 서버.                                    |

직원 설정을 재사용한다고 다른 프로젝트의 소스·대화·기밀 자료가 자동으로 공유되지 않는다.
사용자가 승인한 노하우만 공유 지식으로 남긴다.

## 5. MVP 기능 요구

### 5.1 회사와 프로젝트 — R-006~009, R-025, R-029

- 회사 구성은 프로젝트 단위 또는 프로젝트 묶음 단위로 선택할 수 있다.
- 기존 저장소를 연결하여 작업할 수 있다. 로컬과 SSH 원격 선택을 모두 지원한다.
- 아이디어에서 새 프로젝트를 시작할 수 있다. PM과 요구사항을 정리하고 지침·팀·업무로 이어진다.
- 새 프로젝트를 만드는 과정과 기존 프로젝트를 선택하는 진입점을 구분한다.
- 외부 IDE로 코드를 확인·수정하는 사용 흐름을 방해하지 않는다.
- 새 프로젝트의 원격 저장소 생성이나 외부 공개는 생성 요청만으로 자동 허용하지 않는다.

### 5.2 직원 관리 — R-014~~015, R-018~~019, R-021

- 이름·역할·모델·스킬·지침을 가진 직원을 구성하고 프로젝트에 배정한다.
- 기존 직원을 다른 프로젝트에서 재사용하거나, 이를 바탕으로 튜닝한 직원을 만든다.
- 원본 직원 변경은 파생 직원에 자동 덮어쓰기하지 않는다. 내용을 보고 선택해서 반영한다.
- 프로젝트별 대화·자료·기억은 분리한다. 공통 노하우 공유는 사용자 승인 후 수행한다.
- PM이 새 직원을 필요로 하면 역할·모델·필요 이유를 제안하고 승인 후 생성한다.
- 외형을 바꾸더라도 직원의 역할·지침·배정·업무 기록은 유지되어야 한다.

### 5.3 직접 지시와 PM 위임 — R-016~017, R-020, R-035

- 특정 함수 구현 같은 요청을 해당 직원에게 직접 전달한다.
- 여러 역할이 필요한 요청은 PM이 계획·배정·인계하며 진행한다.
- PM은 맡긴 범위에서 자율 진행한다. 막힘·중요 결정·별도 권한이 필요한 경우 질문한다.
- 독립 업무는 병렬 실행한다. 선행 결과가 필요한 업무는 그 결과를 기다린다.
- 사용자가 최대 동시 실행 수를 설정할 수 있다. 초과 업무는 대기하며 누락되지 않는다.
- 반복 실패는 정해진 횟수 이후 보고한다. 무한 재시도하지 않는다.
- 대기·작업 중·사용자 응답 대기·검토 요청·완료·실패·중단을 혼동 없이 표시한다.
  정확한 상태 이름과 전환 규칙은 상세 설계에서 확정한다.

### 5.4 실행 권한과 완료 — R-022~024

- 기본안은 작업용 브랜치의 수정·테스트·커밋은 자동, 기본 브랜치 병합·푸시·배포는 승인이다.
- 사용자가 프로젝트별 옵션으로 자동 실행과 승인 경계를 선택할 수 있다.
- 파일 대량 삭제·요청 범위 확대·새로운 유료 서비스 사용 등은 기본적으로 질문한다.
- 완료 판정은 다음 중 선택한다.
  - 결과를 검토 요청으로 두고 사용자 승인 후 완료.
  - 정해진 검증을 통과하면 완료 처리하고 보고.
- 자동 완료는 병합·푸시·배포 허가를 대신하지 않는다.
- 보고 형식 제안: 변경 요약, 가능한 경우 실행 화면/미리보기, 실제 테스트 결과와
  미검증 항목, 리뷰 결과. 작업 종류별 검증 기준은 상세 명세가 필요하다.

### 5.5 사무실과 시각화 — R-026, R-036~037

- 참고 이미지 같은 도트 캐릭터와 기본 사무실을 제공한다.
- 작업 상태에 따른 애니메이션과 말풍선/알림을 실제 업무 상태에 연결한다.
- 직원 클릭으로 대화·현재 업무를 확인하고, 질문/알림에서 답변·승인으로 이동한다.
- 프로젝트 선택에 따라 해당 팀과 진행 상황을 표시한다.
- 목록/보드에서도 업무를 확인한다. 시각화만 보고 상태를 추측해야 하는 구조로 만들지 않는다.
- 꾸미기 편집 UI는 MVP에 넣지 않는다.
- 추후 배경·가구/아이템·아바타 변경을 추가할 수 있도록 표현 요소의 분리를 고려한다.
  구체적인 레이어·컴포넌트 분리는 설계 단계에서 정한다.
- 분리의 목적은 배경, 가구/아이템, 직원 외형, 업무 상태 표시를 각각 바꿀 수 있게 하는 것이다.
  예를 들어 김코딩의 아바타를 교체해도 같은 직원의 지침·대화·진행 중 업무는 유지되고,
  사무실 배경을 교체해도 직원 클릭과 질문·승인 알림은 계속 동작해야 한다.
- 외형 교체 때문에 업무 처리나 직원 설정을 다시 만들어야 해서는 안 된다.
  이 요구가 범용 테마 엔진·플러그인 시스템·아이템 상점의 선행 구현을 의미하지는 않는다.

### 5.6 대화와 보고 — R-027~028, R-030

- 직원과의 1:1 대화, 프로젝트 단체방, 업무별 스레드를 제공한다.
- 직원끼리 실제로 교환한 메시지·업무 인계를 볼 수 있다.
- 정리된 보고를 대화와 구분하여 별도로 볼 수 있다.
- 대화·보고에서 관련 업무와 담당 직원을 찾을 수 있어야 한다.
- Otter 안에서 생성한 기록은 유지한다. 외부 CLI의 기존 대화 이관은 MVP에서 제외한다.
- 직원 대화는 실제 교환 기록을 뜻하며, 모델 내부 사고 과정을 표시한다는 뜻이 아니다.

### 5.7 문서·지침·스킬 — R-004, R-019, R-031

- 목표·요구사항·지침·스킬 문서를 GUI에서 직접 작성·수정한다.
- 직원에게 자연어로 문서 수정·지침 반영을 요청할 수 있다.
- 문서가 적용되는 회사·프로젝트·직원의 범위를 이해할 수 있어야 한다.
- 프로젝트를 넘는 공통 노하우 공유에는 사용자 승인을 적용한다.
- 기존 저장소의 지침 파일과 GUI 편집의 동기화, 충돌 처리, 우선순위는 미확정이다.
  문서 편집 허용과 코드 편집기 제공은 구분한다.

### 5.8 실행 지속과 재접속 — R-033~034

- 창 닫기는 작업 중단이 아니다. 로컬 실행은 백그라운드에서 유지한다.
- 완전 종료 시 실행 중인 로컬 작업을 알리고 확인받는다.
- 원격 실행은 접속 앱의 수명과 분리하며, 원격 실행부가 살아 있는 동안 유지한다.
- 다시 접속하면 진행 상태·질문·결과를 복원한다.
- 연결이 끊겼다는 이유만으로 같은 업무를 중복 실행해서는 안 된다.
- 실행부 자체가 중단된 작업을 복구할 때의 자동 재실행 정책은 기술 검증 후 결정한다.

## 6. 대표 사용자 흐름

1. **기존 로컬/원격 프로젝트**: 실행 환경 선택 → 폴더로 저장소 선택 → 회사 구성 →
   직원 배정 → 직접 지시 또는 PM 위임 → 진행 확인 → 설정된 방식으로 결과 검토.
2. **아이디어에서 시작**: 아이디어 입력 → PM과 요구사항 정리 → 목표·지침·계획 작성 →
   저장 위치/프로젝트 구성 → 필요한 신규 직원 승인 → 개발·테스트·리뷰·보고.
3. **직원 재사용**: 기존 김코딩 선택 → 다른 프로젝트에 배정 또는 튜닝한 직원 구성 →
   새 프로젝트 맥락에서 작업 → 원본 개선 시 변경 내용을 확인하고 선택 반영.
4. **지침 수정**: 문서를 직접 수정하거나 직원에게 요청 → 변경 내용 확인/반영 →
   적용 범위 확인. 원본 파생/공유 노하우에 관한 승인 원칙은 유지.
5. **자리 비움**: 작업 중 창 닫기 → 실행부에서 진행 → 질문이 필요한 업무는 대기 →
   재접속하여 답변 및 결과 확인. 독립 업무 진행과 권한 정책은 별도로 유지.

## 7. 도출된 품질 조건

아래는 구현·테스트에 반영할 검토 조건이며, 현재 기능이 이미 구현됐다는 설명이 아니다.

- **실행의 진실성**: 말풍선·진행·대화·보고는 실제 이벤트와 연결한다. 연출용 대화를
  실제 협업처럼 표시하거나 수행하지 않은 테스트를 성공으로 표시하지 않는다.
- **프로젝트 격리**: 회사 묶음·직원 재사용·병렬 실행이 다른 프로젝트의 자료를 자동으로
  공유하거나 기존 작업 파일을 덮어쓰는 원인이 되지 않아야 한다.
- **병렬 작업 안전성**: 같은 파일에 대한 충돌과 외부 IDE의 수정 내용을 감지/보호한다.
  워크트리 등 구체적인 격리 수단은 기술 설계에서 결정한다.
- **정책의 효력**: 승인 필요 작업은 승인 전에 실행하지 않는다. 정책 변경을 이용해
  이미 거부한 작업을 몰래 재실행하지 않는다.
- **종료·복구 안전성**: UI 종료·네트워크 단절·실행부 종료를 구분한다. 중복 실행과
  기록 손실을 방지하고, 복구 불가능한 실행을 완료로 표시하지 않는다.
- **자격 증명과 데이터**: 계정·SSH 자격 증명이 대화·보고·공유 지식·로그에 노출되지
  않도록 한다. 원격 실행부를 무인증 공개 서비스로 노출하지 않는다.
- **측정의 정직성**: 확인할 수 없는 사용량·잔여 구독량·비용을 정확한 수치처럼 표시하지 않는다.
- **초기 진입**: 도구 미설치·미로그인·접속 실패 시 해결할 다음 행동을 안내한다.
  설치/로그인 자동화 범위는 기술 검증 항목이다.
- **시각화 접근성**: 애니메이션을 보지 않아도 상태·질문·담당자를 텍스트와 목록에서 확인한다.

## 8. 제안 기본값 — 사용자 최종 확인 전

상세 옵션을 모두 질문으로 늘리지 않기 위해 아래 기본값을 제안한다.
확정된 옵션 제공 요구와 구분하며, 정리본 검토 시 변경할 수 있다.

| 항목            | 제안                                                                 | 이유/남은 경계                                                   |
| --------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 완료 방식       | 최초에는 사용자 검토 후 완료                                         | 설정에서 자동 완료를 선택할 수 있음                              |
| 동시 실행       | 사용자 작업공간 전체에서 최대 2개 실행부터 시작                      | PM을 포함한 활성 실행 기준. 환경별 추가 제한은 기술 검증 후 결정 |
| 반복 실패       | 같은 업무의 자동 재시도 최대 2회 후 보고                             | 기존 실행이 살아 있는지 확인하기 전 중복 재시도 금지             |
| 설정 업데이트   | 실행 중 업무에는 시작 시 설정 유지, 선택한 변경은 다음 실행부터 적용 | 권한 철회·비상 중단 같은 즉시 제어는 별도 규칙 필요              |
| 프로젝트 저장소 | 최초에는 프로젝트당 Git 저장소 1개                                   | 여러 저장소를 하나의 프로젝트에서 공동 작업할 필요는 미확정      |
| 초기 PM         | 사용자 확인을 거친 기본 PM 구성으로 시작                             | 첫 직원이 없는 상태에서 프로젝트를 시작하는 진입점 필요          |
| 문서 변경       | 직원이 변경안을 만들고 차이를 보여준 후 반영                         | 기존 파일 충돌과 공통 지식 승인은 별도로 적용                    |
| 회사 구성       | 생성 시 1개 프로젝트/프로젝트 묶음 선택                              | 운영 중 구성 전환과 기록 이동은 아직 미정                        |
| 보고            | 업무 결과·막힘·승인 필요 시 생성, 대화와 분리                        | 정기 보고·이메일/외부 메신저 통지는 기본 범위로 가정하지 않음    |

기능을 끄거나 한도를 바꿀 수 있다는 요구가 무제한 실행·기밀 정보 공유·무인증 공개를
포괄적으로 허용한다는 뜻은 아니다. 사용자 옵션과 실행 환경의 보안 제한을 함께 정의해야 한다.

## 11. MVP 완료 검증 기준 — 검토용

아래 시나리오가 통과해야 제품의 핵심 컨셉을 실제로 구현했다고 판단한다.
자동화 테스트의 합성 실행과 실제 Codex를 사용한 수용 테스트를 구분한다.

| ID   | 시나리오                | 통과 조건                                                                                              |
| ---- | ----------------------- | ------------------------------------------------------------------------------------------------------ |
| A-01 | 기존 로컬 프로젝트 시작 | 폴더 선택부터 직원에게 요청하고 실제 결과를 확인하기까지 코드 편집기 없이 진행 가능                    |
| A-02 | 원격 프로젝트 시작      | SSH 환경의 저장소에서 작업하며, 로컬과 원격 대상이 명확하게 표시됨                                     |
| A-03 | 새 아이디어에서 시작    | 빈 프로젝트에서 PM과 요구사항·지침·팀·업무를 구성하고 실제 개발 결과까지 이어짐                        |
| A-04 | 직원에게 직접 지시      | 해당 직원의 대화·업무·실행·결과가 연결되고 잘못된 프로젝트로 전달되지 않음                             |
| A-05 | PM 위임                 | 역할별 계획·배정·인계·테스트·리뷰가 수행되고, 신규 직원은 승인 전에 생성되지 않음                      |
| A-06 | 병렬 작업·한도          | 독립 업무가 실제로 동시에 실행되고, 한도 초과 업무는 대기하며 기존 파일을 침범하지 않음                |
| A-07 | 승인과 완료 옵션        | 승인 필수 작업은 승인 전 미실행. 두 완료 모드가 구분되며 자동 완료가 배포 권한을 우회하지 않음         |
| A-08 | 직원 재사용·파생        | 조정한 직원이 다른 프로젝트에서 동작하고, 원본 변경은 선택 반영되며 프로젝트 기억이 섞이지 않음        |
| A-09 | 문서 두 편집 방식       | 직접 편집과 직원에게 수정 요청이 모두 가능하고, 적용 대상과 최종 반영 내용을 확인 가능                 |
| A-10 | 사무실·메신저·보고      | 캐릭터 조작으로 실제 업무/대화/승인에 접근하며, 직원 간 교환 기록과 보고를 별도로 확인 가능            |
| A-11 | 종료·재접속             | 창 닫기 중 작업 유지, 완전 종료 확인, 원격 실행 유지 및 재접속 복원. 중복 실행 없음                    |
| A-12 | 실패·정직한 상태        | 반복 실패 제한 후 보고. 연결 끊김·실패·완료를 구분하고 미실행 테스트를 성공으로 표시하지 않음          |
| A-13 | 외형 변경 대비          | 설계 검토에서 배경·아바타·아이템 교체가 업무/직원 기록 변경을 요구하지 않음을 확인. 꾸미기 UI는 불필요 |
| A-14 | 배포 및 환경            | 확정할 지원 OS에서 설치·실행·접속·종료를 검증하고, 실제 Codex와 SSH 환경으로 대표 흐름을 확인          |

실제 제공자 실행·원격 접속·유료 사용을 수반하는 검증은 테스트 대상과 권한을 정한 후 수행한다.
이 문서를 작성한 것만으로 위 항목이 통과했거나 실제 실행 권한이 부여된 것은 아니다.

## 12. 다음 단계

1. 이 정리본의 MVP 범위와 8절 제안 기본값을 검토한다.
2. 영향이 큰 기술 검증 항목을 확인하고, 제약이 있으면 요구를 조용히 축소하지 않고 사용자에게 알린다.
3. 회사/프로젝트 생성 → 사무실 → 업무/대화 → 보고/승인의 화면 흐름을 설계한다.
4. 확정한 화면 흐름과 실행 경계를 바탕으로 구현 명세 및 단계별 개발 계획을 작성한다.

인터뷰 단계의 산출물은 요구사항 문서였으며, 이후 별도 재구현 시작 요청에 따라 개발로 이어간다.
기존 사용자 데이터 삭제·외부 배포·원격 푸시는 구현 시작만으로 수행하지 않는다.
