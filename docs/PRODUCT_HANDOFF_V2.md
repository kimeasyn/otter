# Otter v2 — 제품 컨셉·현재 구현·상세 기능 명세

기준일: 2026-09-13 · 다른 ChatGPT 세션과 제품 발전 방향을 논의하기 위한 전달 문서

이 문서는 저장소에 접근할 수 없는 사람도 현황을 이해하도록 작성했다. **기획 의도, 현재 구현, 검증 수준, 앞으로의 제안을 구분한다.** 과거 요구사항 문서의 ‘미정/TODO’가 이후 구현된 경우 이 문서의 현재 상태를 우선한다. 공개 출시 완료나 모든 OS에서의 동작 보증을 의미하지 않는다.

## 1. 먼저 읽을 요약

Otter는 **사람 한 명이 AI 직원에게 개발을 맡기고, 대화·지침·업무·보고를 GUI로 관리하는 작업공간**이다.

- 첫 번째 컨셉: **IDE without code / develop without code**.
- 두 번째 컨셉: **Managing visualized agents like company**.
- 코드가 없는 서비스를 만든다는 뜻이 아니다. 실제 코드는 AI가 수정하고 테스트한다. 사람이 코드를 직접 읽고 고칠 때는 VS Code 같은 외부 IDE를 쓴다.
- 직원, 회사, 사무실은 실제 역할·프로젝트·업무 상태를 친숙하게 표현하는 UI다. 가짜 직원 대화나 연출용 진행률을 보여주는 경영게임은 아니다.
- 첫 사용자는 Codex CLI를 사용하는 개발자인 제작자 본인이다. 회사 업무와 사이드 프로젝트에 먼저 사용하고, 비슷한 니즈의 개발자에게 배포하고 싶다.
- 장기적으로는 비개발자의 체계적인 바이브 코딩, AI 직원 기반 1인 사업 플랫폼을 지향한다. 현재는 개발 프로젝트 관리에 집중한다.
- 설치형 macOS/Windows 앱이 기본 제품 방향이다. 현재 사용 중인 것은 Linux 실행부에 브라우저로 접속하는 개발 프리뷰다. Electron 설치형 코드와 패키징 경로도 있지만 대상 OS의 출시 수용 검증은 남아 있다.
- 실제 제공자 연동은 Codex 우선이다. Claude·OpenRouter는 아직 미구현이다.
- 프로젝트/직원/대화/PM 협업/승인/문서/Git 반영/원격 실행의 코드가 있으나, **프로덕션급 무인 개발·배포 서비스로 완성된 상태는 아니다.**

## 2. 제작자가 중요하게 여기는 원칙

1. 사용자가 코드를 보지 않고도 개발을 진행할 수 있게 한다. 내장 코드 편집기·디버거를 만드는 방향으로 제품을 확장하지 않는다.
2. IDE의 장점인 폴더 선택, 작업 맥락 유지, 빠른 이동, 찾기 쉬운 동작을 가져온다. IDE의 화면 복잡도를 그대로 복제하지 않는다.
3. 직원에게 직접 작은 일을 맡기거나, PM에게 여러 역할의 일을 통째로 맡기는 두 흐름을 지원한다.
4. PM은 맡긴 범위에서 자율적으로 진행하고, 막히거나 중요한 결정이 있을 때 질문한다. 계획 단계마다 체크박스를 누르게 하는 방식은 피한다.
5. 신규 직원 생성은 역할·모델·필요 이유를 제안한 뒤 승인받는다.
6. Git 반영·푸시·배포와 완료 판정은 사용자 옵션을 제공한다. ‘검사 통과’와 ‘외부 공개 허가’는 서로 다르다.
7. 직원 설정을 재사용하더라도 프로젝트별 대화·자료·기억은 자동으로 섞지 않는다.
8. 지침은 직접 편집하거나 직원에게 ‘이 내용을 지침에 반영해줘’라고 요청할 수 있다.
9. 사무실 시각화는 실제 업무로 연결되어야 한다. 꾸미기 때문에 실행 로직이나 직원 정체성을 바꾸지 않는다.
10. 사용자 저장소와 기존 변경을 보호한다. 프로젝트를 Otter 목록에서 치워도 실제 파일을 삭제하지 않는다.

## 4. 핵심 개념과 데이터 관계

```text
사람 한 명
 ├─ 직원 라이브러리: 재사용할 이름·역할·모델·지침·스킬·외형
 │   └─ 파생 직원: 기반 설정과 버전을 기록하고 별도로 조정
 └─ 회사: 프로젝트 하나 / 여러 프로젝트 묶음
     ├─ 승인된 회사 공유 지식
     └─ 프로젝트: 실행 환경 하나 + Git 저장소 하나(개발 단계)
         ├─ 배정: 직원 원본의 설정 사본 + 이 프로젝트의 외형
         ├─ 문서: 목표·요구사항·프로젝트 지침·선택한 공유 지식 등
         └─ 업무: 담당 배정·요청·실행 회차·작업 브랜치·상태
             ├─ 대화·질문·승인
             ├─ 결과 보고·검증 결과·Git 반영 결과
             └─ PM 하위 업무와 선행 업무 관계
```

- **직원 ≠ 세션 ≠ 업무**: 직원은 재사용하는 역할 설정, 업무는 실제 요청 단위, Codex 스레드/턴은 실행 수단이다.
- **원본 직원 ≠ 프로젝트 배정**: 원본을 고쳐도 기존 프로젝트 설정이 자동 변경되지 않는다. 차이를 보고 선택 반영한다.
- **같은 회사 ≠ 모든 맥락 공유**: 회사의 공유 지식도 다른 프로젝트에 자동 주입하지 않는다.
- **실행 환경 ≠ 브라우저를 연 PC**: 서버 프리뷰의 ‘로컬’은 그 서버다. 폴더 탐색도 선택한 실행부의 파일시스템 기준이다.
- **기록 복원 ≠ 자동 재실행**: 재접속으로 상태를 읽는 것과 중단된 에이전트를 다시 실행하는 것은 별개다.

## 5. 상세 기능 명세

### F-01. 회사·프로젝트 시작과 보관

- 회사 생성 시 프로젝트 하나를 운영하는 회사 또는 프로젝트 묶음 회사를 선택한다.
- 시작 방식은 기존 Git 저장소 연결, 새 저장소 생성, 아이디어에서 시작으로 나뉜다.
- 실행 환경을 먼저 구분한다. 로컬 설치 앱은 네이티브 폴더 선택, 웹/원격은 해당 실행부의 폴더 탐색을 사용한다.
- 개발 프로젝트는 하나의 저장소에 연결한다. 동일 경로 중복 등록과 단일 프로젝트 회사의 추가 등록을 막는다.
- 회사 생성은 성공하고 프로젝트 연결만 실패했다면 같은 회사를 재사용한다. 성공한 부분을 없애거나 중복 생성하지 않는다.
- 프로젝트 보관은 목록에서 숨기는 동작이다. 저장소·작업 브랜치·문서·대화는 삭제하지 않는다. 보관 해제도 제공한다.
- 진행/대기 업무나 미확인 외부 작업이 있으면 안전하게 처리하기 전 보관을 제한한다.
- 운영 중 회사 구성 전환, 회사 간 프로젝트 이동, 한 프로젝트의 다중 저장소 관리는 별도 완성 기능이 아니다.

### F-02. 아이디어 회의실

- 아이디어·프로젝트 이름과 초기 PM을 정한다. 기존 직원 또는 새 PM을 사용할 수 있다.
- PM 배정과 실제 모델 인터뷰 시작은 구분된다. 준비 화면을 여는 것만으로 개발하지 않는다.
- PM에게 아이디어를 전달하고 같은 대화에서 질문에 답한다.
- PM은 목표·요구사항·프로젝트 지침·개발 계획의 변경안을 제안하고 필요한 직원의 채용을 제안한다.
- 문서·채용 제안은 사용자가 승인해야 반영된다. 인터뷰 단계는 개발/외부 서비스 실행 권한이 아니다.
- 네 문서의 내용, 팀 구성, 남은 승인과 실행 상태를 확인한 뒤 저장 위치를 확정해 Git 개발 프로젝트로 전환한다.
- 저장하지 않은 문서 초안이나 진행 중인 인터뷰/승인이 있으면 전환을 막는다. 인터뷰 기록은 유지한다.
- 실제 Codex와 모든 대상 OS에서 이 전체 흐름의 성공을 검증한 상태는 아니다.

### F-03. 직원 생성·배정·원본 편집·파생

- 설정 항목: 이름, 역할, Codex 모델, 지침, 스킬·전문 지식, 아바타.
- ‘스킬’은 현재 직원에게 전달되는 텍스트 설정이다. 스킬 패키지 설치기나 마켓플레이스가 아니다.
- 직원 라이브러리에서 기존 직원을 프로젝트에 배정하거나 새 직원을 만든 뒤 배정한다.
- 생성 후 배정만 실패하면 이미 만든 직원을 재사용한다.
- 프로젝트 설정 편집은 그 배정만 바꾸고, 원본 편집은 라이브러리 직원만 바꾼다.
- 파생 직원은 기반 직원 ID·버전·설정 기준을 보존한다. 역할·지침 등을 조정해 독립적으로 사용할 수 있다.
- 이름·역할·모델·지침·스킬의 차이를 비교해 선택한 항목만 가져온다. 이미 실행 중인 작업의 설정을 몰래 교체하지 않는다.
- 편집/비교 기준 버전 이후 원본이나 대상이 바뀌면 충돌로 거절한다. 오래된 화면의 저장으로 타인의 변경을 덮어쓰지 않는다.
- 외형은 기존 비교 항목과 별개로 저장한다. 프로젝트 외형 수정은 다른 프로젝트나 직원 원본을 바꾸지 않는다.
- 편집창 닫기/Esc/메뉴 이동 시 초안을 환경·프로젝트·대상별 메모리에 보존한다. 다시 열면 작성 내용과 원래 기준 버전이 복원되며 명시적으로 초안을 버리고 최신 설정을 열 수 있다. **직원 설정 초안은 새로고침/탭 종료 후 복원을 보장하지 않는다.**

### F-04. 모델 조회·선택

- 모델 설정을 열면 선택한 실행 환경의 설치된 Codex에 `model/list`를 요청한다.
- 목록 조회와 선택은 단일 드롭다운이다. 직접 텍스트 입력은 없다.
- 조회된 목록에 있는 모델만 UI에서 선택한다. 기존 값이 목록에 있으면 유지한다.
- 기존 값이 없거나 목록 밖이면 재선택해야 저장할 수 있다. 로딩·실패·빈 목록에서는 유효한 모델 없이 저장하지 않는다.
- 실패/빈 목록일 때 재조회 버튼을 제공한다. 원격 실패 시 로컬 목록으로 대체하지 않는다.
- 조회는 모델 턴을 실행하지 않는다. 카탈로그에 있다는 사실이 해당 계정의 실제 호출 성공·잔여 사용량을 보장하지는 않는다.
- 이것은 설정 폼의 선택 제한이다. PM 도구 등 모든 서버 입력 경로에서 모델 카탈로그를 강제 검증하는 전역 허용 목록은 아니다.

### F-05. 도트 사무실·아바타

- 프로젝트 팀을 도트 캐릭터와 책상으로 표현하고, 클릭하면 직원 대화로 이동한다.
- 작업 중·대기·검토 요청 등의 표시와 말풍선은 실제 업무 상태에 연결한다.
- 연결 단절 시 마지막 확인 상태로 표시하고 활동 애니메이션을 멈춘다.
- 상태를 텍스트와 업무 목록에서도 제공한다. 그림만 보고 상태를 추측할 필요가 없게 한다.
- 데스크톱 대화 폭을 넓히고 모바일에서는 대화를 사무실 위에 배치한다. 업무에서 대화를 열면 확대 모드로 진입하고 사무실로 돌아갈 수 있다.
- 기본/안경/단발/곱슬머리/모자/헤드셋 총 6종이다. 셔츠/정장/카디건/멜빵/야구 재킷/후드로 의상을 구분한다.
- 직원 생성·프로젝트 설정·원본/파생 편집에서 좌우 캐러셀로 선택한다. 현재 이름·의상·순서를 보여주고 순환 이동 및 키보드 방향키를 지원한다.
- 외형 선택만으로 저장하지 않는다. 사무실·직원 목록·대화가 같은 SVG 표현을 사용한다.
- 의상을 개별 조합하거나 색을 편집하는 기능은 없다. 현재는 캐릭터별 프리셋이다.

### F-06. 대화·업무 요청

- 직원 1:1, 프로젝트 대화, 직원 간 메시지를 구분하고 업무별로 필터링한다.
- 새 업무와 기존 업무 이어가기를 구분한다. 다른 채널에서 기록을 보고 있으면 원래 업무 대화로 이동하도록 한다.
- 직접 요청 또는 PM 위임을 선택한다. 텍스트 입력은 Enter 전송, Shift+Enter 줄바꿈이며 한글 조합 중 Enter는 전송하지 않는다.
- 사용자/직원 메시지는 좌우로 구분한다. 대화 크게 보기를 지원한다.
- 실행 중 추가 지시는 같은 활성 턴에 전달하는 흐름이 있다. 정상 접수되지 않은 요청을 성공으로 표시하지 않는다.
- 중단/실패한 업무는 실행 종료가 확인되고 재개 가능한 상태에서 추가 지시로 이어간다. 기존 작업 폴더와 대화는 유지한다.
- 문서·대화 초안은 탭의 `sessionStorage`와 메모리로 보존한다. 메뉴 이동·동일 탭 새로고침은 지원하지만 탭 종료·다른 기기 동기화는 보장하지 않는다.
- 직원 간 대화는 실제 도구로 교환한 메시지다. 모델 내부 사고 과정이나 보이지 않는 협업을 추측해 표시하지 않는다.
- 대화는 CommonMark 기반 제목·목록·코드·링크를 표시한다. HTML 실행과 이미지 자동 로드는 차단한다. 로컬 파일 참조는 이름과 경로 복사를 제공하며 파일 뷰어/파일 실행으로 연결하지 않는다.

### F-07. 업무 실행과 대기열

- 각 업무는 격리된 Git worktree에서 실행한다. 사용자 원본 작업 폴더에 직접 모든 변경을 쏟아붓지 않는다.
- 업무 요청 시 직원 설정·문서·정책을 스냅샷으로 기록한다. 사용자 후속 요청은 최신 설정을 적용하는 새 실행 회차가 될 수 있다.
- 기본 동시 실행 한도 2, 자동 재시도 한도 2이며 설정에서 변경한다. 초과 업무는 큐에서 기다린다.
- 한 직원의 실행 순서와 의존 관계를 고려한다. 원격 실행 예약도 전체 한도 관리와 연결된다.
- 재시도는 종료가 확인되고 명령/도구 실행이 없었던 제한적인 일시 오류에만 적용한다. 인증/권한/모델 오류나 외부 효과가 있었을 수 있는 요청을 무조건 재실행하지 않는다.
- 응답 유실은 접수 기록으로 대조한다. 같은 요청의 중복 실행을 줄이며, 결과를 확정할 수 없으면 확인이 필요한 상태로 남긴다.

### F-08. PM 협업과 인계

- PM은 현재 프로젝트의 실제 직원·문서·업무 ID를 조회한다.
- 기존 직원에게 범위가 정해진 하위 업무를 배정하고 선행 업무를 지정한다. 독립 작업은 병렬 진행한다.
- 하위 업무의 결과 커밋을 후속 직원/리뷰어/PM에게 인계한다. 단순히 메시지만 전달하고 코드 결과를 무시하는 구조가 아니다.
- PM은 기다리는 동안 실행 자리를 양보한다. 결과/승인 결정이 생기면 같은 PM 대화로 돌아와 진행한다.
- 직접 업무 직원에게 무제한 재위임 권한을 주지 않는다. PM의 한 목표에서 하위 업무 수 등에 상한을 둔다.
- 신규 직원은 `역할·모델·지침·필요 이유`를 제안하고 승인받는다.
- 문서 수정과 공유 지식도 제안/승인 흐름을 사용한다.
- 인계 충돌은 보존하고 다음 행동을 요구한다. 자동으로 사용자 파일을 버려 충돌을 해결하지 않는다.

### F-09. 업무 보드와 상태

- 업무 검색, 담당 직원 필터, 상태 필터, 확인할 업무 바로보기를 제공한다.
- 보드는 진행 중 / 확인할 업무 / 완료·인계로 묶는다.
- 세부 상태는 업무 대기, 작업 중, 답변 필요, 검토 요청, 완료, 실패, 중단, 팀 결과·결정 대기, 인계 완료, 확인 필요 등이다.
- 업무에는 대화, 작업 폴더 IDE, 검토, 작업 브랜치, 가능한 경우 원본 반영/복구 동작이 연결된다.
- 선택한 업무 대화의 ‘제목 변경’으로 최대 80자의 제목을 저장할 수 있다. 버전을 확인하고 제목 메타데이터만 수정하므로 원문 요청·대화·실행 상태는 유지한다. 자동 AI 제목 생성은 없고 최초 제목은 요청 첫 줄을 사용한다.
- 실패 이유는 모델 접근·인증·연결 같은 일부 유형을 한국어로 요약하고 원문은 접어 둔다. 모든 오류 형식을 이해하는 진단기는 아니다.
- 모델 오류의 설정 바로가기는 해당 업무 담당자의 프로젝트 편집창을 직접 연다.
- 사무실의 질문/승인/검토 수와 업무 목록의 실패 포함 확인 대상 수는 집계 범위가 다르다. 숫자만 같게 맞춰 의미를 왜곡하면 안 된다.

### F-10. 승인과 완료 검토

- Codex의 명령·파일 변경·추가 접근 요청을 표시한다. 요청 범위와 현재 업무/실행 환경의 연결을 확인하고 승인 또는 거절한다.
- 파일 변경은 실제 내용과 대상 경로를 확인하게 한다. 긴 내용은 접어서 볼 수 있다.
- 지원 가능한 일회성/현재 턴 권한만 처리한다. 세션 전체/영구 허용을 일회성 승인으로 오인하지 않는다.
- 미지원 권한·다른 실행 환경·오래된 턴·작업 폴더와 연결되지 않은 요청은 안전하게 승인할 수 없는 것으로 처리한다.
- 수동 완료는 확인창에 고정한 실행 회차·결과 커밋·검증 결과에 대한 승인이다. 도중에 결과가 바뀌면 이전 확인으로 완료하지 않는다.
- 단순 중복 체크박스는 줄이고 명시적인 실행 버튼으로 통합했지만, 외부 전송·위험 권한·비용 관련 동의까지 제거하지는 않는다.

### F-11. 독립 검증과 자동 완료

- 수동 검토 또는 지정 검증 통과 후 자동 완료를 프로젝트별로 선택한다.
- 검증은 이름·실행 파일·인수·시간 제한으로 설정한다. 문자열을 자동으로 셸 명령으로 해석하지 않는다.
- 결과 커밋을 별도 작업 공간에 가져와 모델 생성 없이 제한된 명령 실행으로 확인한다.
- PM은 하위 업무마다 전체 검사를 반복하기보다 통합 최종 결과를 검증한다.
- 종료 코드, 대상 커밋, 검증 중 결과 변경 여부 등을 확인한다. 미검증은 통과가 아니다.
- 검증 환경의 도구·의존성·샌드박스 준비가 필요하다. 네트워크나 패키지 설치를 자동 허용하지 않는다.
- 현재 호스트의 일부 제한 실행 검증이 샌드박스 초기화 문제로 막혔던 기록이 있다. 모든 실제 환경에서 검증 성공이 입증된 것은 아니다.

### F-12. 결과 보고

- 대화와 별도 화면에서 결과 보고·확인 필요·Git/검증 등의 실제 기록을 확인한다.
- 업무 범위, 종류, 제목/내용/담당 검색을 지원한다.
- 과거 작성 당시의 기록과 현재 업무 상태를 구분한다. 과거 실패 보고를 현재 성공으로 덮어쓰지 않는다.
- 직원의 주장과 Otter의 별도 검증 결과는 구분한다. ‘완료했다고 보고함’은 ‘사용자 승인/검사 통과’와 다르다.
- 최신 결과 보고와 선택한 업무 대화에서 기존 검토 확인창을 직접 열 수 있다. 오래된 결과 보고에는 현재 결과를 승인하는 버튼을 중복 표시하지 않는다.
- 보고 본문도 안전한 CommonMark를 사용한다. GFM 표 등 확장 문법은 아직 지원하지 않는다.
- 실제 결과 페이지를 자동 기동해 안전하게 미리보기하는 범용 기능은 아직 없다. 파일 결과와 보고를 확인하고 필요하면 외부 IDE를 사용한다.

### F-13. 문서·저장소 지침

- 프로젝트 목표·요구사항·지침을 GUI에서 직접 수정한다. 직원에게 수정안을 제안하게 할 수도 있다.
- 직접 저장/제안 승인과 저장소 파일 반영을 구분한다. 문서 저장만으로 사용자 원본 파일을 자동 수정하지 않는다.
- 저장소 루트의 `AGENTS.override.md`, `AGENTS.md`를 우선순위대로 발견한다.
- 파일과 문서를 비교해 가져오거나 명시적으로 원본 파일에 반영한다. 외부 변경과 버전 충돌을 감지한다.
- 원본 반영 전 복구 사본을 Git 내부 전용 위치에 보존한다. 링크/과도한 크기/잘못된 인코딩 등은 제한한다.
- 연결된 지침은 새 업무/재개 시 작업 브랜치에 적용하되, 해당 브랜치에서 따로 수정된 내용을 자동 덮어쓰지 않는다.
- 하위 폴더 지침 전체 동기화, 모든 제공자 스킬 형식의 가져오기·편집은 지원 범위가 아니다.

### F-14. 회사 공유 지식

- 직원 제안 또는 사용자 작성 → 공유 본문 검토·승인 → 회사 라이브러리 → 다른 프로젝트에서 선택 적용.
- 소스·대화·파일 경로를 자동 첨부하지 않는다. 일부 자격 증명 패턴을 검사하지만 기밀 정보 전체를 자동 판별할 수는 없다.
- 가져온 지식은 프로젝트 문서 사본이다. 원본 수정이나 공유 중지가 이미 적용한 문서를 몰래 바꾸거나 삭제하지 않는다.
- 공유 중지는 새로운 적용을 막는 것이며 과거 실행 기록에서 내용을 회수하는 기능이 아니다.
- 같은 회사의 환경 간 재사용은 지원하지만 회사 간 지식 마켓플레이스는 아니다.

### F-15. Git 원본 반영·푸시·불확정 결과

- 작업 결과를 사용자 원본에 병합하는 동작과 원격 Git 서버로 푸시하는 동작은 별개다.
- 원본 반영 전 대상 폴더·등록 브랜치·커밋·변경 파일을 확인한다. 사용자 미커밋 변경을 자동 stash/커밋/삭제하지 않는다.
- 확인한 두 커밋과 변경 트리를 고정하고, 그 사이 원본/업무가 바뀌면 다시 확인한다. PM 하위 업무는 최종 PM 결과를 통해 반영한다.
- 푸시는 실제 주소와 브랜치·전송 이력을 확인하고 승인한다. 기존 원격 이력을 덮어쓰는 강제 푸시, 원격 브랜치 삭제, 태그 전체 전송을 제공하지 않는다.
- Git 인증은 해당 실행 환경의 기존 인증을 사용한다. URL에 비밀번호/토큰을 넣는 방식은 거부한다.
- Git 훅·사용자 정의 필터/원격 도우미 등 지원하지 않는 저장소 조합은 외부 IDE에서 처리해야 한다.
- 푸시는 CI/CD·자동 배포·유료 작업을 유발할 수 있다. Git 전송 성공을 외부 자동화 성공으로 표시하지 않는다.
- 응답 유실/프로세스 종료 미확인은 자동 재실행하지 않고 실제 Git 결과 대조로 확인한다.
- 시각적인 전체 Git 커밋 그래프/브랜치 탐색기는 현재 구현 기능으로 간주하지 않는다.

### F-16. 완료 후 자동 반영과 배포

- 원본 반영·푸시·배포를 프로젝트 정책에서 각각 수동/자동으로 정한다. 기본값은 모두 수동이다.
- 정책은 승인 이후 새로 받은 최종 업무에 적용한다. 과거 업무에 소급해 외부 동작을 실행하지 않는다.
- 수동 완료면 사용자 검토, 자동 완료면 지정 검증 통과 후 다음 단계를 진행한다. 다른 업무나 미확정 외부 동작이 있으면 기다린다.
- 정책 변경/해제는 이전 정책에 따른 자동 진행을 중단하는 보호와 연결된다.
- 배포는 설치된 실행 파일의 절대 경로·인수·시간 제한으로 실행한다. 명령·폴더·커밋·실행 파일을 확인하고 별도 외부 영향 동의를 받는다.
- **배포 명령은 실행 계정의 호스트 권한으로 실행하며 Codex 샌드박스 안에 제한되지 않는다.**
- 배포 인수는 기록에 남으므로 비밀을 넣지 않는다. 표준 출력/오류는 비밀 노출 방지를 위해 수집·표시하지 않는다.
- 종료 코드 0은 명령 종료이지 서비스 건강 상태 확인이 아니다. 실패/시간 초과/미확정은 무조건 재배포하지 않는다.
- POSIX에서는 같은 프로세스 그룹의 잔존 여부도 확인한다. Windows·별도 세션·외부 비동기 작업의 전체 생명주기까지 보장하지 않는다.

### F-17. 실행 환경·진단·원격 지속

- 로컬, SSH, WSL 실행 환경을 구분한다. 주소·표시 이름·실행부 위치/Node 경로 등 해당 환경 설정을 관리한다.
- SSH는 기존 SSH 키/설정/에이전트를 사용한다. 호스트 키 검증을 자동 우회하지 않는다.
- 원격 사용자 전용 위치에 실행부 코드를 배치하고 SSH 통로로 통신한다. 제공자 인증 파일을 로컬 앱으로 복사하지 않는다.
- 원격은 자체 기록을 보유하고 화면에는 마지막 조회 캐시를 둘 수 있다. 끊김을 실패/완료로 간주하지 않는다.
- 연결만 끊는 것과 실행부를 중단하고 예약을 반환하는 것은 다르다. 실행 중인 원격 코드를 자동 교체하지 않는다.
- Codex 준비 상태 검사: CLI 연결·계정 설정·제한된 OS 기본 명령 실행을 확인한다. 실제 모델 접근/잔여량 검사는 아니다.
- 환경별 Codex 실행 파일 경로를 설정할 수 있다. 저장만으로 실행/로그인을 하지 않으며 실패 시 다른 실행 파일로 자동 대체하지 않는다.
- 앱 종료 시 로컬/WSL 중단과 SSH 지속을 구분한다. 원격 서버 자체가 꺼지면 작업 지속을 보장하지 않는다.

### F-18. 설치형 수명주기·백업

- Electron 창 닫기는 백그라운드 유지, 완전 종료는 진행 중 로컬 작업 확인과 안전한 종료 절차다.
- 화면 프로세스 오류 시 다시 불러오기/백그라운드 유지/완전 종료의 복구 흐름이 있다.
- 실행/배포/Git 처리의 종료를 확인하지 못하면 DB와 잠금을 유지한다. 강제 잠금 삭제를 정상 복구 절차로 안내하지 않는다.
- 설치형에서 로컬 SQLite 기록 사본을 네이티브 파일 저장으로 내보낸다. 전체 로컬 기록과 원격 캐시를 포함하며 실제 저장소/작업 파일/원격 DB/인증 파일은 제외한다.
- 사본은 암호화되지 않는다. 기존 파일을 덮어쓰지 않고 DB 검사와 해시를 확인한다.
- 백업 파일의 자동 복원/업무 재개는 미구현이다. 보존용 사본을 실행용 DB로 바로 여는 것도 차단한다.
- OS별 설치·제거·업데이트·GUI 종료 수용 검사는 여전히 필요하다.

## 8. 실제 구현 구조 — 개발자용

- 활성 UI: `apps/web/src/v2`의 React + TypeScript. Vite로 빌드한다. 서버 상태 조회와 요청은 React Query 및 기존 API 유틸리티를 사용한다.
- 실행부: `apps/worker/src`의 Node.js ESM. HTTP/SSE, Node 내장 SQLite, Git CLI, 설치된 Codex App Server 표준입출력 연결을 사용한다.
- 데스크톱: `apps/desktop/src`의 Electron main/preload. 제한된 네이티브 폴더/실행 파일 선택, 외부 IDE, 백업, 창/종료를 연결한다.
- 주요 실행 모듈: `company.mjs`(도메인), `runner.mjs`(실행/큐/협업), `codex.mjs`(제공자 연결), `cowork.mjs`(협업 도구), `remote.mjs`(환경 연결).
- 안전한 부가 작업은 `verification/merge/push/deployment/git-recovery/instructions/knowledge/request-journal` 모듈에 나뉜다.
- DB: 회사·프로젝트·직원·배정·문서·업무·메시지·보고·승인·환경·공유 지식, 이벤트, 접수 기록, 원격 캐시, 메타데이터를 저장한다. 레코드 버전으로 변경 충돌을 확인한다.
- 기본 실행부 데이터는 `~/.otter-v2`, 환경 변수 `OTTER_V2_DATA`로 분리 가능하다. 설치형은 Electron 사용자 데이터의 v2 위치를 사용한다.
- 개발 실행: Node.js 24 이상, pnpm 10, Git 필요. `pnpm build` 후 `pnpm start`, 기본 주소 `http://127.0.0.1:4318`.
- 개발 프리뷰는 토큰 수동 입력 없이 HttpOnly 쿠키/출처·호스트 검사를 사용한다. 무인증 공개 인터넷 서버로 바인딩하는 제품이 아니다.
- 설치 앱에도 Git·Codex·프로젝트별 도구가 모두 내장되는 것은 아니다. 사용자의 실행 환경 준비가 필요하다.
- 과거 Rust/Tauri 기반 v1 소스/문서는 남아 있지만 현재 v2 제품 구조로 혼동하면 안 된다. v1 DB 자동 이관은 미구현이다.

## 9. 검증 수준과 출시 전 빈칸

‘코드 존재’, ‘합성 제공자/자동화 검사 통과’, ‘실제 Codex 작업 성공’, ‘모든 대상 OS 출시 수용 통과’는 서로 다른 단계다.

- macOS/Windows 설치·사용·업데이트·제거, WSL 및 실제 원격 조합의 대표 흐름 검증은 남아 있다.
- 전체 에이전트 명령에 대한 파일 삭제·비용·네트워크·Git/배포 정책의 완전한 기술적 강제는 미완료다. 에이전트 지침과 Otter가 직접 실행하는 동작의 강제를 구분해야 한다.
- 공개 배포용 서명·공증·자동 업데이트·지원 OS/CPU 확정·라이선스 고지·안전한 복원 절차는 별도 작업이다.
- 이번 통합 변경은 전체 135개 테스트(실행부 73/UI 49/데스크톱 13), 정적 검사·빌드를 통과했다.
- `scripts/smoke-v2-ux-round2.mjs`는 별도 임시 HTTP/SQLite/Git 프로젝트에서 초안 복원·메뉴 복원·모바일 메뉴·담당자 설정 바로가기·Markdown·보고/대화 검토창·제목 저장·모바일 고정 저장을 검사한다. 실제 모델 턴이나 사용자 업무 승인은 실행하지 않는다.
- 이번 변경은 웹 빌드와 개발 프리뷰 실행부에 반영했다. 기존 기록의 재시작 전후 해시가 동일함을 확인했으며 설치 패키지는 다시 만들지 않았다. Git 커밋/푸시도 수행하지 않았다.

### 추가 논의가 필요한 제품 공백 — 구현 약속 아님

1. **결과물 확인**: 코드 없이 일하는 제품이라면 웹앱 화면/스크린샷/테스트 리포트를 어디까지 안전하게 보여줄 것인가?
2. **처음 쓰는 사람의 준비 과정**: Git·Codex 설치/로그인·권한 실패를 어떤 수준까지 앱이 안내하거나 자동화할 것인가?
3. **직원 운영의 차별점**: 단순 역할 프롬프트 모음에서 더 나아가 기본 팀·직무 템플릿·반복 업무를 제공할 것인가?
4. **진행 상황 이해**: 작업 중이라는 상태 외에 목표·계획·결과·막힘을 어느 정도 구조화해서 보여줄 것인가?
5. **비용과 통제**: 정확한 구독 잔여량을 알 수 없는 환경에서 시간/실행 수/추정치/사용자 한도 중 무엇을 제공할 것인가?
6. **업무 수명주기**: 오래된 실패·취소 업무를 보관하거나 목표별로 묶는 정책은 무엇인가? 재실행과 새 업무의 경계는 충분히 이해되는가?
7. **프로젝트와 회사**: 여러 프로젝트를 묶어 볼 실제 사용 이유와 회사 단위 요약·운영 지표가 필요한가?
8. **Git 시각화**: 사용자가 이전에 원한 커밋 트리를 결과 검토에 어떻게 연결할 것인가? 전체 Git 클라이언트로 커지지 않게 범위를 정해야 한다.
9. **신뢰할 수 있는 완료**: 테스트 통과와 요구사항 충족을 구분해, 사용자가 코드 없이도 승인할 근거를 무엇으로 제공할 것인가?
10. **배포와 복원**: 기능 확대보다 먼저 실제 개인 PC에서 설치·업데이트·백업·복원·실패 복구를 완성해야 하는가?

내장 IDE를 만드는 제안, 사용량을 근거 없이 정확하게 표시하는 제안, 자동 승인으로 모든 마찰을 제거하는 제안은 제품 원칙과 충돌할 수 있다.

## 11. 다른 ChatGPT 세션에 그대로 사용할 요청문

> 첨부한 문서는 내가 개발 중인 Otter의 현재 컨셉·기능·제약이다. 코드 저장소를 볼 수 있다고 가정하지 말고, 문서에서 구현됨/미검증/TODO를 구분해서 이해해 줘.
>
> 컨셉은 ‘IDE without code’와 ‘AI 직원을 회사처럼 시각적으로 관리’하는 것이다. 내장 코드 편집기를 만들려는 것이 아니며, 처음에는 내가 Codex로 회사 업무와 사이드 프로젝트를 편하게 진행하는 데 집중한다. 장기적으로 비개발자와 AI 직원 기반 1인 사업까지 보고 있다.
>
> 지금은 코드를 작성하지 말고 제품 기획 파트너로 대화해 줘. 먼저 핵심 사용 흐름과 가장 큰 공백을 짧게 정리한 뒤, 영향이 큰 미결정 사항부터 나를 인터뷰해 줘. 이미 구현된 기능을 새 제안처럼 반복하지 말고, 새 제안은 문제/대상 사용자/사용 흐름/기존 기능과의 차이/범위/부작용/수용 기준으로 설명해 줘. 답을 모르면 가정임을 표시하고, 회사별 비밀 자료나 계정 정보를 요구하지 마.
>
> 논의가 끝나면 다른 개발 에이전트에게 전달할 추가 작업 지시서를 만들어 줘. 필수와 후속을 나누고, 현재 동작 중 무엇을 유지/변경할지와 구현하지 않을 범위를 명시해 줘. 테스트 통과나 OS 지원 상태를 문서에 없는 근거로 확정하지 마.

## 13. 저장소 내 근거 문서

- `docs/REQUIREMENTS_V2.md`: 인터뷰 원문 요구와 결정 기록.
- `docs/MVP_REQUIREMENTS_V2.md`: 최초 MVP 범위/수용 기준. 이후 구현과 다를 수 있는 역사적 기준.
- `README.md`: 현재 실행·기능별 사용법과 제한.
