# Otter 재정의 — 요구사항 인터뷰

작성일: 2026-09-11

상태: 1~8차 기본 인터뷰 정리 완료. [MVP 요구사항 정리본](MVP_REQUIREMENTS_V2.md) 검토 단계.
구체적인 구현 명세 또는 정리본 전체에 대한 최종 승인을 의미하지 않는다.

기존 PRD·구현은 참고 자료로 보존한다. 기존 기능이나 예시 이미지에 등장하는 항목을
자동으로 새 버전의 필수 요구사항으로 승계하지 않는다. 이번 단계에서는 제품 코드와
실행 환경을 변경하지 않는다.

## 1. 제품의 중심

사용자가 코드를 직접 읽거나 편집하지 않고도, AI 에이전트에게 일을 맡기고 대화·지침·
진행 상황·결과를 GUI에서 관리하는 개발 작업공간.

- 1차 컨셉: **IDE without code / develop without code**.
- 2차 컨셉: **managing visualized agents like company**.
- 코드가 생성되지 않는다는 뜻이 아니다. 코드는 에이전트가 작업하며, 사람이 직접
  확인하거나 수정할 때는 우선 VS Code 같은 외부 IDE를 사용한다.
- 제품의 중심은 에이전트 관리와 프로젝트 진행의 편의성이다.
- 회사·직원·부서·사무실과 타이쿤/경영게임의 친숙한 표현을 차용한다.
  기본 도트 사무실과 실제 작업 상태 표현은 MVP에 포함하고, 꾸미기는 후속으로 둔다.
- 장기 비전: AI 직원을 운영하여 1인 사업을 할 수 있는 플랫폼.
  이는 지향점이지, 첫 버전에서 모든 사무 업무·사업 운영을 구현한다는 뜻은 아니다.

| --- | --- | --- |

| R-002 | 배포 대상 | 동일한 에이전트 관리 니즈가 있는 다른 개발자에게 배포할 의향이 있다. |
| R-003 | 확장 사용자 | 비개발자도 AI 코딩 도구를 활용해 체계적으로 바이브 코딩할 수 있게 하고 싶다. 첫 출시의 지원 수준은 미정이다. |
| R-004 | 핵심 편의 | 에이전트, 대화 세션, 지침, 프로젝트 진행을 GUI에서 쉽게 확인하고 관리한다. |
| R-005 | 코드 편집 범위 | 우선 외부 IDE에 맡긴다. 내장 편집기를 기본 전제로 설계하지 않는다. |
| R-006 | 작업 기준 | Git repository 기반이다. |
| R-007 | 로컬 프로젝트 | 파일/폴더 탐색으로 로컬 저장소를 선택하고 작업한다. |
| R-008 | 원격 프로젝트 | SSH 또는 클라우드 서버에 있는 저장소도 관리한다. 7차 인터뷰에서 SSH 원격 작업의 MVP 포함을 확정했다. 자체 호스팅 서비스 요구와는 구분한다. |

| R-010 | 기존 도구 활용 | Codex/Claude CLI로 일하는 것과 유사한 실제 작업 수행을 기대한다. 구체적인 연동 프로토콜은 아직 결정하지 않는다. |
| R-011 | 계정/비용 | 사용자가 가진 Codex·Claude·OpenRouter 이용 권한을 우선 활용하고 싶다. 제공자별 인증·과금·지원 범위는 각각 검증한다. |
| R-012 | 상시 실행 | 로컬 작업 PC가 꺼지거나 잠든 동안의 실행 지속은 보장하지 않는다. 7차 인터뷰에서 접속 앱 종료와 별개로 살아 있는 원격 실행부의 작업을 유지하는 방향을 승인했다. Otter 자체 클라우드 호스팅은 MVP 필수가 아니다. |
| R-013 | 배포 방식 | 2차 답변에서 설치형 기본 + 로컬/WSL/SSH 작업 실행부 방향을 수용했다. Docker/브라우저형은 후속 옵션으로 둔다. 기술 스택과 OS별 구현 범위는 미정이다. |
| R-014 | 직원 재사용 | 프로젝트 A에서 만든 직원의 스킬·지침 등을 다른 프로젝트에서도 재사용할 수 있어야 한다. |
| R-015 | 직원 파생 | 기존 직원을 기반으로 다른 프로젝트에 맞게 튜닝·조정한 직원을 만들 수 있어야 한다. 상속과 유사한 사용 경험을 원하며, 구현상 클래스 상속을 요구하는 것은 아니다. |
| R-016 | 직접 지시 | 특정 함수 구현 같은 업무는 사용자가 담당 직원을 직접 선택해 요청할 수 있어야 한다. |
| R-017 | PM 위임 | 로그인 기능의 계획·화면·API·테스트·리뷰처럼 여러 역할을 포함하는 업무는 PM에게 맡겨 분담시킬 수 있어야 한다. 직접 지시와 PM 위임을 모두 지원한다. |
| R-018 | 파생 직원 업데이트 | 원본 직원의 스킬·지침 변경은 자동 덮어쓰기하지 않고, 변경 내용을 확인한 뒤 사용자가 선택해서 반영한다. |
| R-019 | 프로젝트 기억 분리 | 직원 설정을 재사용하더라도 프로젝트별 대화·자료·기억은 분리한다. 사용자가 승인한 공통 노하우만 공유 지식으로 남긴다. |
| R-020 | PM 자율 진행 | PM은 요청한 범위 안에서 계획·배정·작업을 이어가고, 막히거나 중요한 결정이 필요할 때 질문한다. 매 단계의 사용자 승인을 기본 흐름으로 요구하지 않는다. 중요한 결정과 별도 실행 권한의 기준은 추가 확인한다. |
| R-021 | 신규 직원 생성 승인 | PM은 신규 직원이 필요하면 역할·모델·필요 이유를 제안하고, 사용자 승인 후 생성한다. |
| R-022 | Git 실행 권한 설정 | 기본 제안은 작업용 브랜치에서 수정·테스트·커밋을 자동 진행하고, 기본 브랜치 병합·원격 푸시·배포는 승인받는 것이다. 사용자가 프로젝트별 옵션으로 자동 실행/승인 경계를 선택할 수 있어야 한다. |
| R-023 | 중요한 결정의 기본 경계 | 파일 대량 삭제, 요청 범위 확대, 새로운 유료 서비스 사용 등은 기본적으로 질문한다. 세부 권한 항목과 옵션의 범위는 후속 정의한다. |
| R-024 | 완료 판정 설정 | 결과를 검토 요청 상태로 두고 사용자가 승인해야 완료하는 방식과, 정해진 검증을 통과하면 자동 완료 후 보고하는 방식을 사용자 옵션으로 제공한다. 기본 선택값과 설정 적용 범위는 미정이다. |
| R-025 | 회사 구성 선택 | 프로젝트 하나를 회사 하나로 사용하는 방식과, 여러 프로젝트를 묶어 회사로 사용하는 방식을 사용자가 선택할 수 있어야 한다. |
| R-026 | 조작 가능한 사무실 | 직원 클릭으로 대화·현재 업무를 확인하고, 말풍선/알림에서 질문 답변·승인으로 이동하며, 프로젝트 선택에 따라 해당 팀·진행 상황을 표시하는 메인 사무실 화면을 제공한다. 별도 목록/보드 화면도 제공한다. |
| R-027 | 대화 구조 | 직원과의 1:1 대화, 프로젝트 단체방, 업무별 스레드를 제공한다. 직접 지시와 PM 위임이 각 업무의 논의·보고에 연결되어야 한다. |
| R-028 | 직원 간 대화와 보고 분리 | 사용자가 직원들끼리 주고받는 대화를 확인할 수 있어야 하며, 정리된 보고는 대화와 구분하여 별도로 볼 수 있어야 한다. |
| R-029 | 신규 프로젝트 시작 | 기존 저장소 연결뿐 아니라 아이디어를 바탕으로 새 프로젝트를 바닥부터 시작하는 흐름도 MVP에 포함한다. PM과 요구사항을 정리하고 프로젝트·지침·팀을 구성해 작업으로 이어간다. |
| R-030 | 외부 대화 가져오기 유예 | 기존 CLI에서 진행한 대화의 가져오기·조회·이어 하기는 MVP에서 제외하고 후속 TODO로 남긴다. Otter 안에서 새로 진행한 대화와 업무 기록 관리는 이 제외 범위에 해당하지 않는다. |
| R-031 | 문서의 직접/직원 편집 | 목표·요구사항·지침·스킬 문서는 Otter GUI에서 직접 작성·수정할 수 있고, 직원에게 자연어로 수정·반영을 요청할 수도 있어야 한다. |
| R-032 | MVP 제공자 | 사용자가 현재 사용하는 Codex를 우선 지원한다. Claude 및 OpenRouter는 후속 지원 대상으로 둔다. Claude의 제약에 대한 사용자의 우려는 기술적으로 검증된 제한 사항으로 취급하지 않는다. |
| R-033 | 창 닫기와 종료 | 창을 닫아도 백그라운드 작업을 유지한다. 앱 완전 종료 시 실행 중인 로컬 작업을 알리고 종료 확인을 받는다. 화면을 다시 열면 작업 진행 상황을 복원한다. |
| R-034 | 원격 실행 지속 | 접속 앱을 종료해도 원격 실행부가 살아 있으면 원격 작업을 유지한다. 재접속 시 상태·기록을 확인할 수 있어야 한다. 실행부 자체 종료 후 작업의 자동 재개를 보장한다는 의미는 아니다. |
| R-035 | 동시 작업 및 제한 | 독립적인 업무는 여러 직원이 병렬 실행한다. 사용자가 최대 동시 실행 수를 설정하고 초과 업무는 대기시킨다. 반복 실패는 무한 재시도하지 않고 정해진 횟수 이후 보고한다. 구체적인 기본 수치는 설계 제안으로 남긴다. |
| R-036 | MVP 사무실 표현 | 도트 캐릭터·기본 사무실·작업 상태에 따른 애니메이션·클릭 조작을 MVP에 포함한다. 꾸미기 기능은 TODO로 둔다. |
| R-037 | 외형 변경 대비 | 추후 꾸미기 아이템, 배경 변경, 아바타 변경을 추가할 수 있도록 시각적 요소를 분리 가능한 형태로 준비한다. 구체적인 레이어·컴포넌트 설계는 설계 단계에서 정하며, MVP에 꾸미기 편집기 전체를 구현한다는 뜻은 아니다. |
| R-038 | 1인 운영 | MVP는 사람 한 명이 AI 직원들을 운영하는 제품이다. 다른 사용자에게 개별 설치형으로 배포하되, 여러 사람이 같은 회사를 공동 운영하는 기능과 사람 간 권한 관리는 TODO로 둔다. |

## 3. 설계 방향과 승인 상태

### P-001. 설치형 화면 + 독립된 작업 실행부

상태: 2차 인터뷰에서 제품 방향 수용. 구체적인 구현 구조·기술 선택은 미확정.

- 사용자는 macOS/Windows 설치형 앱으로 시작한다.
- 작업 실행부는 선택한 환경(로컬 PC, WSL, SSH 서버)에서 저장소와 에이전트를 관리한다.
- SSH 서버는 사용자가 보유한 장비일 수 있으며, Otter가 클라우드를 운영할 필요는 없다.
- Docker/브라우저 패키징은 후속 배포 옵션으로 남긴다.
- 이유: 로컬 폴더 선택, 기존 개발 환경 활용, 외부 IDE 연결을 우선하는 사용자 요구와
  맞추기 위한 방향이다. 기술 스택 및 세부 배포 사양은 확정하지 않았다.

### P-002. 화면 종료와 작업 종료 분리

상태: 7차 인터뷰에서 기본 동작 승인.

- 창 닫기는 UI를 닫는 동작이며 백그라운드 작업을 중단하지 않는다.
- 앱 완전 종료 시 진행 중인 로컬 작업을 알리고 종료 확인을 받는다.
- 작업 실행부가 켜져 있으면 진행을 유지하고, UI 재접속 시 진행 상황을 복원한다.
- 작업 PC가 꺼지거나 잠들면 그 환경의 실행 지속은 보장하지 않는다.
- 별도 서버의 실행부가 유지되면 접속 앱 종료와 별개로 서버 작업을 유지한다.
- OS별 트레이/메뉴 막대 동작, 중단 시 안전 처리, 연결 끊김과 실행 실패의 구분,
  실행부 재시작 후 복구 방식은 상세 명세에서 정의한다.

### P-003. 재사용하는 직원 설정과 프로젝트별 작업 맥락 분리

상태: 3차 인터뷰에서 선택적 업데이트와 프로젝트 기억 분리 원칙 승인.

- 재사용 대상인 직원의 기본 설정과 프로젝트별 조정 내용을 구분한다.
- 프로젝트 A에서 만든 직원을 B에서도 재사용하거나, B에 맞춘 파생 직원을 구성한다.
- 기본 설정의 수정은 변경 알림과 내용을 확인한 뒤 사용자가 선택해서 반영한다.
  프로젝트별 조정과 충돌하는 항목의 처리, 실행 중 작업에 반영되는 시점은 추후 정의한다.
- 스킬·지침 재사용이 다른 프로젝트의 대화·소스·기밀 정보까지 자동 공유한다는 뜻은 아니다.
- 프로젝트별 대화·자료·기억은 분리한다. 승인된 공통 노하우만 재사용 가능한 지식으로 남긴다.
  공통 노하우의 제안·검토·저장 방식과 공유 범위는 추후 정의한다.
- 직원의 역할·설정과 개별 대화 세션·실행을 동일한 개념으로 취급하지 않는다.

### 확인된 대표 사용 흐름

- 직접 지시: 사용자가 백엔드 직원 ‘김코딩’에게 특정 함수 구현을 요청한다.
- PM 위임: 사용자가 PM에게 ‘카카오 로그인 기능을 계획·화면·API·테스트·리뷰까지
  진행해 달라’고 요청하면 PM이 업무를 분담한다.
- PM은 요청 범위 안에서 진행하며, 막히거나 중요한 결정이 생길 때만 사용자에게 질문한다.
  계획이나 각 단계마다 의무적으로 승인받는 흐름은 기본값으로 두지 않는다.
- 이 자율 진행 원칙이 직원 무제한 생성, 추가 과금, Git 외부 반영, 배포, 파괴적인 변경까지
  포괄적으로 허용한다는 뜻은 아니다. 신규 직원은 제안 후 승인받으며, Git 실행과 완료
  판정은 사용자가 선택한 정책을 따른다.

### P-004. 권한과 완료 정책의 선택

상태: 4차 인터뷰에서 신규 직원 승인, Git 실행 및 완료 판정의 사용자 옵션 제공 승인.

- Git 실행 권한의 기본안: 작업용 브랜치에서 수정·테스트·커밋은 자동,
  기본 브랜치 병합·원격 푸시·배포는 승인. 프로젝트별로 조정할 수 있다.
- 업무 완료 판정: 사용자 검토 후 완료 / 정해진 검증 통과 후 자동 완료를 선택한다.
  자동 완료가 Git 병합·푸시·배포의 허가를 대신하지는 않는다.
- 제안된 보고 내용: 변경 요약, 가능한 작업의 실행 화면/미리보기, 실제 테스트 결과와
  미검증 항목, 리뷰 결과. 세부 보고 형식과 완료 검증 기준은 추가 정의한다.
- 옵션의 기본값, 적용 단위, 실행 중 정책 변경의 효력, 허용할 수 없는 위험 작업의
  경계는 후속 명세에서 구체화한다. 현재 인터뷰는 실제 작업 실행 권한 부여가 아니다.

### P-005. 회사 화면과 대화 구조

상태: 5차 인터뷰에서 회사 구성 선택, 조작 가능한 사무실, 대화/보고 분리 승인.

- 회사 구성은 프로젝트 1개 단위 또는 여러 프로젝트의 묶음 중 사용자가 선택한다.
  회사 생성 시 선택하는지, 생성 후 전환 가능한지, 기존 배정과 기록의 이동 규칙은 미정이다.
- 여러 프로젝트를 같은 회사로 묶더라도 R-019의 프로젝트 기억 분리 원칙을 없애지 않는다.
- 사무실은 장식용 대시보드에 한정하지 않는다. 직원·질문·승인·업무에 접근하는 메인
  작업 화면으로 사용하고, 목록/보드로도 업무를 확인한다.
- 직원 1:1 대화, 프로젝트 단체방, 업무별 스레드가 실제 업무와 연결된다.
- 직원 간 메시지·업무 인계 등의 대화 기록과 정리된 보고를 별도로 탐색할 수 있게 한다.
  여기서 대화는 실제 교환된 메시지이며, 모델 내부 사고 과정을 표시한다는 의미가 아니다.
- 보고의 작성 주체, 보고 주기, 대화 필터, 사무실 말풍선의 표시 규칙은 상세 UX 단계에서 정의한다.
- 다른 회사로 직원 설정을 가져오는 방식과 회사 단위 공통 지식의 범위는 아직 미정이다.

### P-006. 프로젝트 시작과 문서 관리

상태: 6차 인터뷰에서 신규 프로젝트의 MVP 포함, 외부 CLI 대화 이관 유예,
문서의 직접 편집과 직원을 통한 편집 병행 확인.

- 기존 프로젝트: 저장소 연결 → 현황 파악 → 직원 배정 → 업무 진행.
- 신규 프로젝트: 아이디어 입력 → PM과 요구사항 정리 → 프로젝트·지침·팀 구성 → 업무 진행.
  신규 직원 생성에는 R-021의 제안/승인 원칙을 적용한다.
- 새 프로젝트의 경로 선택, Git 초기화, 원격 저장소 생성/연결 시점은 상세 흐름에서 정의한다.
  신규 프로젝트 생성이 원격 서비스에 저장소를 자동 생성할 권한을 의미하지는 않는다.
- 문서 직접 편집과 직원에게 수정 요청하는 방식을 함께 제공한다.
- 기존 저장소의 지침 파일을 보여주고 변경 사항 확인 후 반영하는 방향은 제안 상태로 두며,
  파일 동기화, 편집 충돌, 지침 적용 우선순위 및 적용 시점은 별도 명세가 필요하다.
- 외부 CLI 대화 이관은 MVP에 넣지 않는다. 기존 저장소 열기와 Otter 자체 대화 기록까지
  제외하는 것으로 해석하지 않는다.

### P-007. 병렬 작업과 시각화의 MVP 경계

상태: 8차 인터뷰에서 병렬 작업·실행 제한, 기본 도트 사무실, 꾸미기 유예,
외형 변경을 고려한 분리, 1인 운영 범위 승인.

- 독립적인 업무는 병렬로 진행하고, 의존 작업은 선행 작업의 결과를 기다린다.
- 사용자가 정한 동시 실행 한도를 초과한 업무는 대기하며, 반복 실패는 제한 후 보고한다.
  한도 적용 범위·기본 수치·충돌 처리 방식은 정리본의 제안 또는 기술 검증 항목으로 둔다.
- 기본 도트 캐릭터·사무실·상태 애니메이션·클릭 조작을 제공한다.
- 추후 배경·아이템·아바타 교체가 직원의 정체성·지침·업무 기록을 바꾸지 않도록 한다.
  이는 외형 변경 요구를 구체화한 설계 조건이며, 구체적인 구현 방식은 미정이다.
- 꾸미기 도구와 다중 사용자 공동 운영은 MVP에 넣지 않는다.

## 4. 혼동하지 않아야 할 기술적 경계

### 실행 장소와 모델 제공처

PC 종료 후 계속 작업하려면 켜져 있는 작업 실행 환경이 필요하다. 이것이 자체 LLM
서빙을 반드시 요구하지는 않는다. 사용자가 보유한 서버에서 작업을 실행하고, 모델은
기존 외부 제공자를 사용하는 구조도 가능하다. 단, 계정 정책과 해당 연동 방식이 이를
허용하는지 별도로 검증해야 하며, 일반 SSH 접속만으로 프로세스 지속을 보장하지 않는다.

### 구독 로그인과 API 사용 권한

OpenAI Docs 스킬로 확인한 공식 문서는 Codex의 ChatGPT 구독 로그인과 사용량 기반
API 키 로그인을 구분한다. 일반 API 키 사용은 별도 API 과금이므로, 구독을 보유했다는
이유만으로 범용 API 사용 권한까지 있다고 가정하지 않는다.
[Codex 인증 공식 문서](https://learn.chatgpt.com/docs/auth).

Codex에는 클라이언트 연동을 위한 App Server 인터페이스가 있으나, 전송 방식별 안정성
제약도 문서화되어 있다. 이번 단계에서 특정 SDK나 프로토콜로 구현 방식을 확정하지 않는다.
[Codex App Server 공식 문서](https://learn.chatgpt.com/docs/app-server).

Claude 및 OpenRouter의 구체적인 인증·연동·과금·재배포 조건은 아직 검증하지 않았다.
기존 계정을 활용하고 싶다는 요구와 실제 지원 가능 범위를 구분한다.

## 7. 인터뷰 이력

- 1차: 대상 사용자, 로컬/원격 작업 환경, OS, 실행 지속성과 기존 계정 활용 의도 확인.
- 2차: 설치형 중심 방향 수용, 직원 설정의 재사용·파생 요구, 직접 지시와 PM 위임의 병행 확인.
- 3차: 원본 변경의 선택적 반영, 프로젝트 기억 분리 및 승인된 노하우 공유, 막힘·중요 결정 시에만 질문하는 PM 진행 방식 승인.
- 4차: 신규 직원의 역할·모델·필요 이유 제안 후 승인, Git 실행 권한 및 완료 판정의 사용자 옵션 제공 승인.
- 5차: 프로젝트 단위/프로젝트 묶음 단위 회사 선택, 조작 가능한 사무실과 목록/보드, 1:1·단체방·업무 스레드, 직원 간 대화와 별도 보고 보기 승인.
- 6차: 아이디어에서 신규 프로젝트를 만드는 흐름의 MVP 포함, 외부 CLI 대화 이관 TODO 분리, 문서 직접 편집과 직원에게 수정 요청하는 방식 병행 확인.
- 7차: Codex 우선 지원, SSH 원격 작업의 MVP 포함, 창 닫기 시 백그라운드 유지·완전 종료 확인·재접속 복원·원격 실행부의 독립적인 작업 유지 승인.
- 8차: 병렬 작업·동시 실행 제한·반복 실패 보고, 기본 도트 사무실, 꾸미기 TODO와 외형 분리 고려, 1인 운영 MVP 승인.

## 8. MVP 우선순위 기록

### 이번 인터뷰에서 MVP 포함을 명시한 사항

- 기존 프로젝트뿐 아니라 새 프로젝트를 바닥부터 시작하는 흐름.
- 문서의 직접 편집 및 직원에게 자연어로 수정 요청하는 흐름.
- Codex 기반 실행, SSH 원격 프로젝트 관리.
- 창 닫기와 작업 종료 분리, 살아 있는 원격 실행부의 작업 유지 및 UI 재접속 복원.
- 독립 업무의 병렬 실행·한도 초과 대기·무한 재시도 방지.
- 조작 가능한 기본 도트 사무실과 작업 상태 표현, 1인 운영.

### MVP에서 제외하기로 명시한 사항

- Otter 외부에서 수행한 기존 CLI 대화의 가져오기·조회·이어 하기.
- Claude 및 OpenRouter 연동: Codex 이후 후속 지원.
- 꾸미기 아이템·배경/아바타 교체 UI 등 꾸미기 기능. 추가 가능하도록 외형 분리는 고려한다.
- 여러 사람의 동일 회사 공동 운영과 사람 간 권한 관리.

### 후속 옵션 또는 검토 대상으로 남긴 사항

- Docker/브라우저 배포판.
- Otter 자체 클라우드 운영·호스팅 및 자체 LLM 서빙.
- macOS·Windows/WSL 및 SSH를 지원 대상으로 두되, 세부 OS 버전·배포 사양·원격 서버
  조건·Codex 인증 및 연동 가능 범위는 구현 전 기술 검증이 필요하다.

나머지 확정된 제품 요구는 2절에 유지한다. 위 목록은 전체 MVP 기능 목록이 아니며,
전체 범위와 검증 기준은 [MVP 요구사항 정리본](MVP_REQUIREMENTS_V2.md)에서 종합한다.
